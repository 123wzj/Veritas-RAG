# 项目学习路线与代码阅读指南

这份文档给后来读项目的人用。目标不是背概念，而是知道：

- 一次文档上传从哪里进、到哪里结束。
- 一次用户提问从哪里进、每一步代码在哪里。
- RAGAS 和检索评估怎么跑、结果怎么看。
- 学习这个项目时应该先看什么、后看什么。

---

## 1. 先记住一句话

这个项目不是“一个 prompt 加一个向量库”。

它更像一条流水线：

```text
文档先入库
  -> 切成适合检索的小块
  -> 保存向量和正文

用户再提问
  -> 先判断该不该查知识库、联网或闲聊
  -> 再找证据
  -> 证据不够就反思重试
  -> 最后按证据生成答案
  -> 再校验答案靠不靠谱
```

学习时不要一上来钻 prompt。先把这条流水线跑通。

---

## 2. 第一条线：文档上传到入库

先从 API 入口看：

```text
backend/api/v1/endpoints/knowledge.py
```

这一步负责接收上传文件、检查大小、保存临时文件，然后调用入库服务。

继续往下看：

```text
backend/services/ingestion/parser.py
backend/services/ingestion/chunker.py
backend/services/ingestion/ingestion.py
```

用大白话说：

1. `parser.py`：把 PDF、DOCX、Markdown、TXT 等文件读成文本。
2. `chunker.py`：把长文本切成 parent 和 child。
3. `ingestion.py`：把 child 向量写入 Chroma，把 parent/child 正文写入 MySQL。

为什么要 parent-child：

- child 小，适合检索。
- parent 大，适合生成答案时补上下文。

所以代码里会经常看到：

```text
child chunk -> Chroma 检索
parent_id -> MySQL 回补正文
```

---

## 3. 第二条线：用户提问到答案

先看 API：

```text
backend/api/v1/endpoints/rag.py
```

这里负责接收问题、创建/读取 session、启动 RAG 图，并通过 SSE 把过程和最终答案返回前端。

然后看状态图：

```text
backend/graph/state/state.py
backend/graph/graph.py
```

`state.py` 是“这次问答的共享草稿纸”。问题、路由、证据、答案、反思次数都放在里面。

`graph.py` 是“流程编排表”。它告诉 LangGraph：

```text
load_memory -> rewrite_query -> decompose_query -> plan_query_route
-> retrieve / web_search / generate_answer
-> judge_evidence -> reflect / generate_answer
-> verify_answer -> write_memory
```

读懂这两个文件，再看节点代码会轻松很多。

---

## 4. 第三条线：Query Rewrite / Decomposition / Route

看这个文件：

```text
backend/graph/nodes/query_nodes.py
```

这里做三件事：

1. 改写问题：把口语化问题变得更适合检索。
2. 拆解问题：把复杂问题拆成多个子问题。
3. 路由规划：判断每个子问题应该走 `chat`、`knowledge_base`、`web_search` 还是 `hybrid`。

学习时重点看这几个函数：

```text
rewrite_query
decompose_query
plan_query_route
route_planned_query
```

大白话：

- 闲聊不要硬查知识库。
- 天气、最新政策这类问题更适合联网。
- 明确问“根据文档”的问题才优先知识库。
- 既要文档又要最新信息，就走 hybrid。

---

## 5. 第四条线：检索、融合、精排、证据

先看真实检索服务：

```text
backend/services/retrieval/hybrid.py
```

这里做 dense / sparse 召回和 Weighted RRF 融合。

再看精排：

```text
backend/services/retrieval/reranker.py
```

最后看图节点：

```text
backend/graph/nodes/retrieval_nodes.py
```

这里把检索结果变成可引用证据：

```text
retrieve_hybrid
-> rerank_candidates
-> pack_evidence
-> judge_evidence
```

大白话：

- `retrieve_hybrid`：先多捞一点候选。
- `rerank_candidates`：再把最像答案证据的排前面。
- `pack_evidence`：给证据编号，比如 `E1`、`E2`。
- `judge_evidence`：判断证据够不够，不够就让后面反思或联网。

---

## 6. 第五条线：Reflection / Web / Generation

证据不够时看：

```text
backend/graph/nodes/reflection_nodes.py
```

它会问：是不是要换个检索词再找一次？是不是该联网？

当前反思最多 3 次。代码里已经做了收口：到上限就不再继续重试，避免撞 LangGraph 的 recursion limit。

联网看：

```text
backend/graph/nodes/web_nodes.py
backend/services/web_search/search_providers.py
```

答案生成和校验看：

```text
backend/graph/nodes/generation_nodes.py
```

大白话：

- `generate_answer`：按证据生成答案，并要求带 `[E#]` 引用。
- `verify_answer`：检查答案是否 grounded、是否 useful。
- 如果答案不靠谱，而且反思次数还没用完，再回到 reflection。

## 7. 配置怎么看

配置统一看：

```text
backend/core/config.py
```

LLM 初始化看：

```text
backend/graph/llm_factory.py
```

当前项目只从根目录 `.env` 加载本地配置。

```text
.env
```

不要再使用：

```text
backend/.env
```

原因很简单：两个 `.env` 容易互相覆盖，排查问题很痛苦。现在统一成根目录一个配置源。

常用配置包括：

```text
LLM_MODEL
LLM_BASE_URL
LLM_API_KEY
DEEPSEEK_FLASH_MODEL
DEEPSEEK_PRO_MODEL
DEEPSEEK_BASE_URL
DEEPSEEK_API_KEY
MAX_REFLECTION_ROUNDS
GRAPH_RECURSION_LIMIT
RAGAS_BATCH_SIZE
RAGAS_RUN_MAX_WORKERS
```

注意：`.env` 是本地秘密配置，已经被 git ignore，不要写进文档和代码。

## 8. 评估代码怎么看

检索评估：

```text
backend/evaluation/import_t2retrieval_dataset.py
backend/evaluation/run_t2retrieval_eval.py
```

生成评估：

```text
backend/evaluation/import_hotpotqa_dataset.py
backend/evaluation/run_ragas_answer_eval.py
```

先理解一个原则：

```text
检索评估看“证据有没有找对”
生成评估看“答案有没有答对、有没有乱编”
```

RAGAS 评估脚本不是只评估一段文本，它会先调用真实 RAG 流程生成答案，再用 RAGAS 打分。

## 9. 推荐学习顺序

按这个顺序看，最省力：

1. `docs/Agentic RAG 实现索引.md`
2. 本文档
3. `backend/core/config.py`
4. `backend/api/v1/endpoints/rag.py`
5. `backend/graph/state/state.py`
6. `backend/graph/graph.py`
7. `backend/graph/nodes/query_nodes.py`
8. `backend/services/retrieval/hybrid.py`
9. `backend/graph/nodes/retrieval_nodes.py`
10. `backend/graph/nodes/reflection_nodes.py`
11. `backend/graph/nodes/generation_nodes.py`
12. `backend/evaluation/run_ragas_answer_eval.py`

每看一个文件，都问自己三个问题：

1. 它接收什么输入？
2. 它往 `RAGState` 写了什么字段？
3. 下一个节点靠这些字段做什么？

能回答这三个问题，就算真的读懂了。

## 11. 当前评估数据怎么选

当前 HotpotQA 200 条适合做“固定回归基准”。

它适合测：

- 多跳问题拆解。
- 证据是否找全。
- 答案是否忠实。
- reflection 是否会失控。

但它不够代表企业落地。

企业评估还要补：

- 中文业务问题。
- 找不到答案的问题。
- 权限隔离问题。
- 表格、数字、日期、版本问题。
- 长文档定位问题。
- 闲聊和联网路由问题。

所以结论是：

```text
HotpotQA 继续保留，用来做回归。
企业落地还要再建一份业务 QA 评估集。
```
