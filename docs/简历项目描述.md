# 简历项目描述

## Agentic RAG 智能知识库问答系统

技术栈：Python、FastAPI、LangGraph、Chroma、MySQL、Redis、SQLAlchemy、OpenAI-compatible LLM、BGE-M3、BGE Reranker、Qwen-VL、SSE。

项目介绍：一个面向个人/企业私域知识库的 Agentic RAG 智能问答系统，用于解决普通 RAG 在“检索召回不准、长文档上下文缺失、复合问题路由粗糙、答案幻觉和引用不可追溯”等方面的问题。系统采用“子块向量检索 + 父块关系库回补 + Agent 控制流”的架构设计，支持文档上传解析、父子分块、混合检索、RRF 融合、重排精排、子问题级路由、证据评估、反思重检索、联网补充、结构化引用生成和会话记忆管理，实现复杂问题按子问题独立检索/联网、再统一汇总为可追溯答案的完整闭环。

- 基于 FastAPI 搭建知识库和问答接口，设计文档上传、知识库管理、会话历史、流式问答等核心 API，支持前端创建知识库、上传文件并基于指定知识库进行增强问答，解决私域文档无法被大模型直接利用的问题。
- 设计并实现 Parent-Child Chunking 分块方案，将子块用于高精度召回、父块用于上下文回补，并将子块向量与检索元数据写入 Chroma、父子块正文写入 MySQL，解决长文档检索中“召回粒度”和“回答上下文”难以兼顾的问题。
- 实现 Dense + Independent Sparse 双路召回机制，默认使用本地 BGE-M3 进行语义向量检索，并在应用层构建词法稀疏召回，配合 Weighted RRF 对多 Query、多通道结果进行融合排序，解决纯向量检索对术语、字段名、版本号等精确关键词命中不稳定的问题。
- 基于 LangGraph 搭建 Agentic RAG 状态机，引入 Query Rewrite、Query Decomposition、Route Planning、Evidence Grading、Reflection、Web Search、Answer Verification 等节点，并将复杂问题升级为 `sub_query_plans` 子问题执行计划，支持 `chat / web_search / knowledge_base / hybrid` 多路由决策，解决传统 RAG 固定“检索一次就回答”、复合问题只能整体处理的流程僵化问题。
- 使用 Reranker 对融合后的候选证据进行精排，并在子块命中后通过 `parent_id` 到 MySQL 回补父块上下文，再按子问题统一封装为 `E1/E2/E3` 证据对象，解决检索结果相关但不一定适合最终回答、以及复合问题各部分证据容易混在一起的问题。
- 设计结构化答案生成与引用机制，要求模型按子问题基于证据输出 JSON，并在关键结论后携带 `[E#]` 内联引用，同时通过 groundedness / usefulness 验证节点判断答案是否被证据支撑，降低大模型幻觉并提升复杂问答结果的可解释性。
- 实现会话与记忆管理能力，支持会话自动创建、历史消息查询、会话标题生成、用户偏好和近期上下文加载，并结合 SSE 向前端推送问答过程事件，提升多轮对话连续性和前后端交互体验。

## 口述版

我做的是一个面向私域知识库的 Agentic RAG 智能问答系统。它和普通 RAG 的区别不是只做“检索一次然后生成”，而是把文档入库、父子分块、Dense/Sparse 混合检索、路由规划、证据评估、反思重检索、生成引用和事实校验串成一个可控闭环。

当前架构里，我把子块向量和检索元数据放到 Chroma，把父块和子块正文放到 MySQL；检索时先召回子块，再根据 `parent_id` 回补父块上下文，最后通过 Reranker 精排和证据判断决定是否生成、反思或联网补充。进一步我把复杂问题改造成“按子问题独立 route / 检索 / 联网 / 证据评审 / 生成，最后统一聚合”的执行模式，解决了复合问题里只回答前半句、后半句缺证据却没有继续补齐的问题。

## 面试重点与回答思路

### 1. 项目和普通 RAG 的区别是什么？

普通 RAG 通常是固定流程：检索一次、拼上下文、生成答案。这个项目是 Agentic RAG，会先做查询改写、问题拆解和路由规划，再根据证据质量动态决定是生成、反思重检索还是联网补充，最后还会做答案验证。现在对复杂问题还支持按子问题独立执行，这样一个问题里既可以有知识库检索部分，也可以有实时联网部分，最后再统一汇总。

### 2. 为什么要做 Parent-Child Chunking？

因为小块适合检索，大块适合生成。只用小块会缺上下文，只用大块会降低召回精度。所以我用 child chunk 做高精度召回，用 parent chunk 回补完整上下文。

### 3. 为什么要做 Dense + Sparse？

Dense 解决语义相似和同义表达，Sparse 解决术语、字段名、版本号、命令等精确关键词命中。企业知识库里这两类需求同时存在，所以需要双路召回再融合。

### 4. 为什么选 RRF 做融合？

Dense 和 Sparse 的分数尺度不一致，直接相加不稳定。RRF 基于排序名次做融合，不强依赖原始分数归一化，工程上更稳，适合作为混合检索的基础融合方案。

### 5. 为什么还需要 Reranker？

召回阶段更关注“别漏”，精排阶段更关注“前几条最能回答问题”。Reranker 能在融合候选里做更细粒度相关性判断，减少低质量上下文进入生成阶段。

### 6. Agent 如何决定下一步？

系统会先做 Evidence Grading，判断证据覆盖度和可回答性。证据够就生成；不够但还能优化检索，就进入 Reflection；如果问题需要实时信息且允许联网，就走 Web Search；生成后还会做 groundedness / usefulness 验证。对于复杂问题，这个判断是按子问题做的，只有所有子问题都覆盖，系统才会进入最终聚合生成。

### 7. 如何控制幻觉？

主要做三层控制：检索前通过 rewrite、decomposition、hybrid retrieval 和 rerank 提高证据质量；生成时要求基于 evidence 输出并带 `[E#]` 引用；生成后再做 groundedness 和 usefulness 验证，不通过就回流反思。

### 8. 为什么用 Chroma + MySQL？

Chroma 负责子块向量检索和 metadata filter，MySQL 负责知识库、文档、父子块正文、会话和用户信息。这样向量检索和业务数据职责清晰，也方便后续替换向量库或扩展权限、审计、评测等能力。
