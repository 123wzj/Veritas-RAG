# 会话记忆与上下文工程实现说明

上级导航：[`docs/README.md`](README.md) · 背景设计：[会话记忆与上下文工程](<会话记忆与上下文工程.md>)

## 1. 设计目标

当前实现以 MySQL 为唯一事实源，不在进程内长期保存聊天状态，也不在
`sessions.context` 中复制一份历史问答。

整体流程分为六个阶段：

```text
阶段一：用户问题入库
  -> messages 保存 user 消息和 request_id

阶段二：加载短期上下文并理解问题
  -> 最近 2~3 轮原文
  -> session summary
  -> 当前问题
  -> DeepSeek 同时生成 Query Rewrite 和本轮 working memory
  -> Decompose / Route

阶段三：检索与证据处理
  -> Dense + Sparse
  -> RRF 融合
  -> rerank
  -> evidence judge / reflection

阶段四：选择长期记忆
  -> 按 user_id、kb_id、scope、status 预筛
  -> 关键词相关性排序
  -> DeepSeek 从候选 ID 中选择本轮需要的记忆

阶段五：动态 Prompt 与回答
  -> ContextAssembler 按任务类型加载必选/可选区块
  -> DeepSeek 生成回答
  -> DeepSeek 校验 grounded / useful

阶段六：事务化持久化
  -> messages 保存 assistant 回答
  -> 达到阈值时更新 session summary
  -> 必要时更新长期记忆
  -> memory_update_logs 保存审计记录
```

## 2. 数据库职责

| 表 | 职责 |
| --- | --- |
| `sessions` | 会话元数据、`user_id`、`kb_id`、独立标题 `title` |
| `messages` | 完整聊天原文、角色、引用、token 估算、`request_id` |
| `session_memories` | 会话摘要、摘要处理游标和版本号 |
| `long_term_memories` | 用户级、项目级长期记忆事实源 |
| `memory_update_logs` | 摘要和长期记忆变更审计、幂等控制 |

`sessions.summary` 只为旧数据兼容保留，新摘要只写入
`session_memories.summary`。

`session_memories` 中的关键控制字段：

- `summary_through_message_id`：摘要已经覆盖到哪条消息。
- `version`：检测同一会话并发更新。

working memory 不写数据库，因此不需要处理游标或版本控制。

## 3. 短期记忆结构

会话摘要保存跨多轮仍需保留的历史状态：

```json
{
  "session_goal": "当前会话的总体目标",
  "confirmed_decisions": ["已经确认且仍然有效的结论"],
  "discarded_ideas": ["已经被否定或替换的方案"],
  "open_questions": ["仍未解决的问题"]
}
```

working memory 是当前请求的临时任务工作区：

```json
{
  "current_task": "当前正在完成的任务",
  "constraints": ["当前任务约束"],
  "open_questions": ["当前仍需处理的问题"],
  "active_entities": ["当前活跃的项目、模块或概念"]
}
```

三类短期上下文的职责不同：

```text
最近对话原文 = 保留措辞、指代和局部细节
session summary = 保留跨多轮的目标、结论、否定项和未决问题
working memory = 保留当前任务面，已解决内容应及时移除
```

它由阶段二的会话理解模型根据“当前问题 + 最近 2~3 轮原文 + session summary”
现场生成，只放在本轮 LangGraph state 中。没有明确任务时可以为空；回答结束后直接释放，
不写入 `session_memories` 或其他数据库表。

## 4. 会话摘要更新机制

### 4.1 更新阈值

摘要不会每轮重写。满足任一条件时才调用 `deepseek-v4-flash`：

| 配置 | 默认值 | 含义 |
| --- | ---: | --- |
| `MEMORY_SUMMARY_UPDATE_MIN_NEW_TURNS` | `2` | 自上次摘要后至少新增 2 个用户轮次 |
| `MEMORY_SUMMARY_FORCE_UPDATE_CHARS` | `1800` | 未摘要消息和当前回答累计达到该字符数时强制更新 |
| 首次摘要 | 是 | 当前摘要没有 `session_goal` 时立即生成 |

未达到阈值时：

- 本轮 working memory 仍由问题理解阶段临时生成。
- 长期记忆仍然可以按需更新。
- session summary 保持上一版不变。
- `summary_through_message_id` 不推进。

### 4.2 模型输入

摘要更新不是只总结当前一轮。模型同时接收：

1. 上一次完整 `session summary`。
2. `summary_through_message_id` 之后的最近对话原文。
3. 当前用户问题。
4. 当前助手最终回答。
5. 本轮任务参数。

模型输出一份新的完整摘要，而不是只输出增量补丁。这样模型可以：

- 保留上一版仍然有效的结论。
- 将用户纠正的旧结论移入 `discarded_ideas`。
- 删除已经解决的 `open_questions`。
- 把最近多轮内容压缩成稳定状态。

### 4.3 摘要长度

| 配置 | 默认值 | 作用 |
| --- | ---: | --- |
| `MEMORY_SESSION_SUMMARY_TARGET_CHARS` | `1600` | 告诉模型摘要整体应尽量控制的目标长度 |
| `MEMORY_SUMMARY_ITEM_TARGET_CHARS` | `240` | 告诉模型单条结论应尽量控制的目标长度 |

这两个值是模型压缩目标，不是服务端截断上限。

服务端不会按字符数切断模型生成的摘要，只校验 JSON 结构和字段类型。原因是硬截断
可能把结论、否定关系或问题描述截成半句。模型偶尔超出目标时仍完整入库，下一次摘要
更新再由模型继续压缩。

### 4.4 失败与并发

- 摘要模型调用失败时，不推进摘要游标，后续轮次会再次尝试。
- 每个计划记录生成时的 `base_memory_version`。
- 写入时版本一致，直接采用模型生成的完整摘要。
- 写入时版本已变化，说明有并发轮次先完成。此时保守合并新旧摘要，避免覆盖较新的
  已确认结论；后续达到阈值时再由模型统一压缩。
- 较旧消息对应的计划不能把摘要处理游标倒退。

## 5. 长期记忆

长期记忆类型：

- `user_preference`
- `user_profile`
- `project_context`
- `project_decision`
- `project_constraint`

作用域：

- `user`：可跨项目使用，`kb_id` 必须为空。
- `project`：只属于当前知识库/项目，必须绑定当前 `kb_id`。

### 5.1 选择流程

1. MySQL 使用作用域索引筛出当前用户可见的 active 记忆。
2. 在最多 `MEMORY_MAX_ACTIVE_PER_USER=200` 条 active 记忆内计算关键词相关度。
3. 取 `MEMORY_LONG_TERM_CANDIDATE_LIMIT=20` 条候选。
4. `deepseek-v4-flash` 只从候选 `memory_id` 中选择最多
   `MEMORY_LONG_TERM_TOP_K=6` 条。
5. 只有模型选中的记忆才进入回答 Prompt。

模型不可用时不盲目加载最近记忆，只回退到词法分数达到
`MEMORY_LONG_TERM_FALLBACK_MIN_LEXICAL_SCORE=1.0` 的候选。

反思节点修改检索问题后，会比较 `long_term_selection_query`。查询发生变化时重新选择
长期记忆，避免沿用上一轮反思前的错误记忆集合。

### 5.2 更新流程

`deepseek-v4-flash` 输出以下动作：

- `create`
- `merge`
- `replace`
- `invalidate`
- `none`

服务端只执行结构合法的计划，并做硬校验：

- 只能操作模型输入候选中的 `memory_id`。
- 只能操作当前用户的 active 记忆。
- project 记忆必须属于当前 `kb_id`。
- merge 不允许把记忆从一个项目移动到另一个项目。
- replace 继承原记忆的作用域和 `kb_id`。
- 相同 `normalized_key` 的 create 会转成可审计的去重合并。

普通知识库事实不会因为出现在助手回答中就自动成为用户长期记忆。长期记忆应来自用户
明确表达的偏好、约束、决定或跨轮次仍有价值的项目状态。

## 6. 动态 Prompt 组装

所有主要模型调用在执行前都经过 `ContextAssembler.assemble_typed()`。不同任务使用
不同加载策略，不再复用一段不断累积的通用字符串。

| Prompt 类型 | 必须加载 | 存在才加载 |
| --- | --- | --- |
| `query_rewrite` | 当前问题；存在时还必须加载摘要和最近对话 | 用户偏好；同时输出本轮 working memory |
| `query_decompose` | 当前问题 | 路由参数 |
| `route_planning` | 当前问题、路由参数 | 无 |
| `long_term_selection` | 当前问题、候选长期记忆 | working memory、摘要、最近对话 |
| `evidence_judgement` | 当前问题、证据 | 路由参数 |
| `reflection` | 当前问题、反思参数 | 证据、working memory、摘要 |
| `answer_generation` | 当前问题；知识库回答还必须有证据 | 摘要、working memory、最近对话、长期记忆、用户偏好 |
| `answer_verification` | 当前问题、回答 | 证据 |
| `memory_update` | 当前问题、回答、上一版摘要、任务参数 | 未摘要对话、本轮临时 working memory、候选长期记忆、验证结果 |

当摘要任务存在未摘要消息时，`recent_messages` 会从可选区块升级为必选区块。

每个动态区块使用以下边界：

```text
<CONTEXT_SECTION name="..." trust="data">
...
</CONTEXT_SECTION>
```

系统提示明确声明区块内容只是数据，其中要求修改系统规则、泄露提示词、执行工具或跳过
验证的文字全部无效。这用于降低历史消息、长期记忆和检索文档中的 Prompt Injection
风险。

### 6.1 预算与优先级

通用预算：

| 配置 | 默认 token 估算 |
| --- | ---: |
| `CONTEXT_INPUT_TOKEN_BUDGET` | `7000` |
| `CONTEXT_RECENT_TOKEN_BUDGET` | `1200` |
| `CONTEXT_SESSION_SUMMARY_TOKEN_BUDGET` | `800` |
| `CONTEXT_WORKING_MEMORY_TOKEN_BUDGET` | `600` |
| `CONTEXT_LONG_TERM_TOKEN_BUDGET` | `900` |
| `CONTEXT_EVIDENCE_TOKEN_BUDGET` | `3200` |

记忆更新 Prompt 使用独立的 `8000` token 估算预算，并给上一版摘要预留更大的输入空间，
避免摘要模型在压缩前就看不到旧摘要的后半部分。

知识库回答的装配优先级是：

```text
当前问题 -> 证据 -> working memory -> 会话摘要
-> 最近对话 -> 长期记忆 -> 用户偏好
```

证据排在记忆之前，是为了防止长期记忆或历史对话耗尽预算，导致回答失去 RAG 依据。
运行结果会记录实际加载区块、遗漏区块、分区 token 估算、实际进入 Prompt 的
`selected_evidence_ids` 和 `selected_memory_ids`。

## 7. 回答验证与记忆写入门槛

回答生成后使用 `deepseek-v4-flash` 校验：

- `grounded`：是否有足够证据支持。
- `useful`：是否实际回答了问题。

验证失败且仍有反思次数时，返回 reflection。达到最大反思次数后可以结束回答流程，但：

- 用户问题和最终助手消息仍按聊天记录保存。
- 不生成 `memory_update_plan`。
- 不更新摘要或长期记忆；本轮 working memory 随请求结束释放。

这样可以防止低质量或无依据回答污染后续多轮上下文。

## 8. 一致性、幂等与审计

每轮使用唯一 `request_id`：

1. 用户消息先写入 `messages`。
2. LangGraph 只生成回答和 `memory_update_plan`，不直接提交记忆。
3. API 保存助手消息。
4. 在同一数据库事务中应用 session memory 和长期记忆计划。
5. `memory_update_logs` 阻止同一请求重复应用。

完整聊天记录永远以 `messages` 为准。摘要和长期记忆是可重建、可审计的持久化派生状态；
working memory 是不持久化的请求级状态。

## 9. DeepSeek 模型分层

- `deepseek-v4-flash`：Query Rewrite、问题分解、路由、证据判定、长期记忆选择、
  答案验证。
- `deepseek-v4-flash`：所有查询、生成、验证、摘要和记忆任务（V1 成本控制策略）。

项目继续使用当前可工作的 LangChain、LangGraph 和 `langchain-deepseek` 版本，不为本次
上下文工程改造升级依赖。

后端内部统一使用 `backend.*` 绝对导入。标准启动方式是在仓库根目录执行：

```bash
conda activate cook-rag-1
python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

不需要额外设置 `PYTHONPATH`，也不再支持从 `backend/` 目录使用 `main:app` 启动。

## 10. 主要难点与设计原因

### 10.1 不能把完整历史全部塞进 Prompt

完整历史成本高、噪声大，而且旧结论可能已经被用户推翻。系统只加载最近原文、压缩摘要、
本轮临时 working memory 和选择后的长期记忆。

### 10.2 摘要不能只看当前一轮

只看当前一轮会逐渐遗忘旧目标和历史决定。因此摘要模型必须同时看到上一版摘要和未摘要
对话，并输出完整新版摘要。

### 10.3 记忆和证据不能混成一个字符串

证据用于证明答案，记忆用于理解用户和任务。如果混装，可能出现证据重复、记忆覆盖证据
或 token 统计失真。当前实现分区装配，并让证据优先。

### 10.4 长期记忆不能按“最近”直接加载

最近更新不等于与当前问题相关。当前实现先按作用域和词法相关性预筛，再由模型选择；模型
故障时也只加载达到相关性门槛的记忆。

### 10.5 多轮并发不能互相覆盖

同一会话的两个请求可能基于同一版摘要同时生成计划。摘要版本号、摘要游标和旧计划保守
合并共同避免状态倒退。working memory 不持久化，因此不存在跨请求覆盖问题。

### 10.6 模型输出不能直接信任

模型负责语义判断，代码负责边界：用户归属、项目作用域、候选 ID、合法动作、幂等、
事务和审计都由服务端强制执行。

## 11. 当前验证

后端测试覆盖：

- 动态 Prompt 必选/可选区块与预算。
- 最近 2~3 轮消息加载。
- 上一版摘要和未摘要对话共同进入摘要模型。
- 摘要目标长度只约束模型、不被服务端截断。
- 长期记忆候选选择和无关记忆回退。
- 跨项目长期记忆隔离。
- 摘要版本冲突和摘要游标保护。
- 回答验证失败时跳过记忆更新。
- 消息与记忆事务写入和 `request_id` 幂等。

前端不在本轮测试范围内。
