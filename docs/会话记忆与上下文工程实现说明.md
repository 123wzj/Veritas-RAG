# 会话记忆与上下文工程实现说明

上级导航：[`docs/README.md`](README.md) · ReAct 总架构：[V1.6 ReAct Agentic RAG 架构重构需求](react-agent/README.md) · 设计总览：[会话记忆与上下文工程](<会话记忆与上下文工程.md>)

> 本文以当前仓库源码为准，同时给出 V1.6 记忆与上下文改造的实现契约。标记为“当前”的内容已经存在，标记为“目标”的内容是后续优化项，不能混写成已实现能力。

## 1. 当前实现边界

当前主链路是 LangGraph 状态图：

```text
load_memory -> rewrite_query -> decompose/route -> retrieve/rerank/evidence
-> load_generation_memory -> generate -> verify -> write_memory
```

当前已经具备：

- `messages` 保存完整用户/助手消息，使用 `request_id` 做幂等。
- `session_memories` 保存 JSON 会话摘要、版本和 `summary_through_message_id` 游标。
- `long_term_memories` 保存 user/project 作用域、类型、置信度、状态、来源和过期时间。
- query rewrite 节点生成 request-scoped working memory。
- 长期记忆先做作用域/状态/过期过滤和词法候选，再由 Flash 模型选择。
- `ContextAssembler.assemble_typed()` 按 prompt type 装配带边界的 section，并记录 token 使用、裁剪和 selected IDs。
- 回答验证失败时不生成记忆更新计划；最终事务写入消息、摘要和长期记忆审计。

当前仍存在的设计差距：

| 差距 | 当前表现 | 目标 |
|---|---|---|
| 三层命名 | 当前文档把“短期记忆”与摘要/最近消息/工作记忆混称 | 明确 request/session/user-project 三个 namespace |
| 长期召回 | 主要是关键词排序，候选默认上限较低 | 词法 + 向量 + freshness + scope 的可解释混合排序 |
| 时效治理 | 有 `expires_at` 和 active 过滤 | 增加 stale 扫描、valid time、supersede 和 tombstone 规则 |
| 上下文预算 | `CONTEXT_INPUT_TOKEN_BUDGET` 当前默认为 7000 | 以 300k 为模型上限，提供 8k/32k/64k/128k 可配置档位 |
| 长历史 | 只加载最近轮次和摘要 | 增加按 session/branch 的历史 recall，明确来源和优先级 |
| 工作记忆 schema | 已有 task/constraints/open_questions/entities | 增加 schema_version、goal、working_plan、current_focus 和过期语义 |

## 2. 数据模型和 namespace

### 2.1 消息与会话

`messages` 是不可替代的事实源。所有原始用户消息和最终助手消息都要落库，不能只保留摘要。读取时必须过滤当前 `request_id`，避免流式请求把尚未完成的用户消息重复加载；分支场景按 `branch_id` 和祖先消息选择可见历史。

`session_memories` 是每个 session 唯一的一行派生状态：

```text
summary                 JSON，见 ss.v1
summary_text            供展示/兼容，不作为唯一事实源
summary_through_message_id
version                 乐观并发版本
updated_at
```

### 2.2 长期记忆

`long_term_memories` 当前已有以下字段：`memory_id/user_id/kb_id/scope_type/memory_type/content/normalized_key/keywords/confidence/source/status/last_confirmed_at/expires_at/source_session_id/source_message_id/superseded_by/access_count/valid_from/valid_to/memory_metadata`。

字段语义必须固定：

- `scope_type=user` 时 `kb_id=NULL`，允许跨知识库加载；`scope_type=project` 时必须匹配当前 `kb_id`。
- `status=active` 才能默认进入召回；`pending_confirmation` 只进入记忆管理页，不进入关键回答上下文。
- `valid_to` 表示事实结束，`expires_at` 表示系统复核时间；到期不等于删除。
- `source_message_id/source_session_id` 是 provenance，不能省略。
- `superseded_by` 用于表达新事实替代旧事实，旧记录保留用于审计。

目标阶段可增加：`embedding_id/last_retrieved_at/decay_score/confirmation_count/visibility`，但不应破坏当前迁移兼容。

## 3. 三层加载协议

### 3.1 阶段 A：加载短期记忆

`load_user_memory` 调用 `memory_service.get_short_term_memory()`：

1. 根据 `user_id + session_id` 校验会话归属。
2. 读取用户画像和 session summary。
3. 从 `messages` 读取最近 `CONTEXT_RECENT_TURNS` 个用户轮次，保留用户/助手成对消息。
4. 不加载长期记忆，只返回空的 `long_term_memories`，避免在 query 尚未改写前误选。
5. `rewrite_query` 将当前问题、摘要和最近消息交给模型，同时生成 working memory。

当前工作记忆兼容结构：

```json
{
  "schema_version": "wm.v1",
  "current_task": "...",
  "goal": "...",
  "constraints": ["..."],
  "open_questions": ["..."],
  "active_entities": ["..."],
  "working_plan": ["..."],
  "current_focus": "..."
}
```

旧数据没有新增字段时按空数组/空字符串读取，不影响兼容。工作记忆只存于 `RAGState.memory_context`，API 结束后释放。

### 3.2 阶段 B：加载长期记忆

`load_generation_memory` 在 query rewrite、decompose、reflection 完成后执行。它把改写问题和子问题合并为 `long_term_selection_query`，如果查询没有变化则复用当前选择结果。

目标候选算法：

```python
scope_candidates = active_memory(user_id, kb_id)
time_candidates = valid_from <= now and (valid_to is null or valid_to > now)
fresh_candidates = expires_at is null or expires_at > now
lexical = bm25_or_keyword(query, content, normalized_key, keywords)
semantic = vector_similarity(query, memory.embedding)
score = 0.45 * lexical + 0.35 * semantic + 0.10 * confidence \
        + 0.05 * scope_bonus + 0.05 * freshness
candidates = top_n(score, n=20)
selected_ids = llm_select_only_from(candidates, max_k=6)
```

服务端在模型返回后再次检查：候选 ID 是否属于当前用户、scope 是否匹配、状态是否仍为 active、时间是否有效。模型不可用时只回退到 lexical score 达标的候选，不加载所有最近记忆。

### 3.3 阶段 C：生成上下文

`generate_answer` 重新调用 `ContextAssembler.assemble_typed("answer_generation")`，以当前问题、证据、工作记忆、session summary、最近消息、选中的长期记忆和用户画像为输入。知识库回答必须有 evidence section；闲聊路由可以没有 evidence，但不能伪造引用。

生成节点应保留：

```json
{
  "loaded_sections": ["query", "evidence", "working_memory"],
  "omitted_sections": ["recent_messages"],
  "missing_required_sections": [],
  "selected_evidence_ids": ["E1", "E2"],
  "selected_memory_ids": ["MEM-1"],
  "token_usage": {"budget": 32000, "used": 8420}
}
```

这些字段写入 trace，便于回答后解释“为什么使用了这条记忆”和“哪一块被裁剪”。

## 4. 三层更新协议

### 4.1 工作记忆更新

工作记忆在 query rewrite 时创建，在 reflection 时按当前证据和缺口修正，在 answer verification 后结束。它不调用独立数据库写入，不进入 `memory_update_logs`。若需要调试，只在 trace 中保存脱敏后的摘要，不保存完整私有推理。

### 4.2 短期记忆更新

`write_memory` 只生成计划，`TurnService.finalize_turn()` 在保存 assistant message 的同一事务中应用：

```text
1. 检查 request_id 是否已完成，已完成则幂等返回
2. 插入 assistant message
3. 读取 session_memory.version
4. 根据阈值判断是否需要摘要
5. 需要时用“上一版摘要 + 游标之后的消息 + 当前问答”生成完整新摘要
6. 版本未变化则写入；版本冲突则保守合并，不回退游标
7. 写 memory_update_logs，提交事务
```

摘要不应每轮重写。当前阈值是新增用户轮次 `2` 或累计字符 `1800`，未来应增加 token 阈值，并优先以 token 作为跨语言稳定指标。摘要更新失败不推进游标，下一轮重试。

### 4.3 长期记忆更新

只有回答验证通过，且当前轮出现用户明确偏好、用户确认、项目决策或约束时，才生成长期记忆计划。模型输出：

```json
{
  "action": "create|merge|replace|invalidate|none",
  "target_memory_id": "仅允许候选 ID",
  "scope_type": "user|project",
  "memory_type": "user_preference|user_profile|project_context|project_decision|project_constraint",
  "content": "一条可独立理解的事实",
  "confidence": 0.0,
  "valid_from": null,
  "expires_at": null,
  "reason": "来源和冲突判断"
}
```

服务端必须执行：

- `create` 的 user/project scope 和 `kb_id` 由当前请求决定，不能由模型跨项目指定。
- `merge/replace/invalidate` 只能操作本次候选中的已有 ID。
- 同一 `normalized_key` 的重复 create 转为可审计 merge。
- inferred 记忆默认 `pending_confirmation`；user_confirmed 才进入 active。
- replace 创建新版本、关闭旧版本并填写 `superseded_by/valid_to`。
- 用户删除写 tombstone/`deleted`，不能让后续摘要自动恢复。
- 所有动作写 `memory_update_logs`，以 `request_id + memory_id + action` 幂等。

## 5. 动态 Prompt 的实现契约

### 5.1 Typed section

`ContextAssembler` 不接受“无限长的 prompt_context”作为唯一入口，而应接受结构化值：

```python
values = {
    "query": query,
    "working_memory": working_memory,
    "evidence": selected_evidence,
    "session_summary": session_summary,
    "recent_messages": recent_messages,
    "long_term_memories": selected_memories,
    "profile": profile,
}
bundle = context_assembler.assemble_typed(
    "answer_generation",
    values=values,
    total_budget=request_budget,
    required_sections={"query", "evidence"},
)
```

每个 section 渲染为：

```text
<CONTEXT_SECTION name="evidence" trust="retrieval">
## 可用证据
[E1] source=knowledge_base; title=...; section=...; content=...
</CONTEXT_SECTION>
```

`trust` 只表示来源类别，不等同于事实正确性；最终回答仍必须经过 evidence judge 和 verification。所有动态数据都放在 system prompt 规定的“数据区”，禁止数据中的文字覆盖系统规则。

### 5.2 Prompt policy

当前 `PROMPT_POLICIES` 已覆盖 query rewrite、decompose、route、long-term selection、evidence judgement、reflection、answer generation、verification 和 memory update。每个 policy 必须定义：

```text
required sections       缺失即不调用模型
optional sections       有空间且有值才加载
section priority        当前问题/证据/记忆的排序
per-section budget      单区上限
total budget            本次请求上限
output schema           结构化结果契约
```

生成答案的推荐优先级：

```text
query -> working_memory -> evidence -> session_summary
      -> recent_messages -> long_term_memories -> profile -> recall_history
```

知识库证据排在记忆之前；长期记忆只能帮助理解用户，不能代替 `E#` 引用。当前问题和必需证据不可因预算不足被静默省略。

### 5.3 300k 分档预算

代码中的 `CONTEXT_INPUT_TOKEN_BUDGET=7000` 是当前保守默认，不代表模型只有 7k 窗口。目标改为配置档位：

| 档位 | 输入预算 | 适用场景 |
|---|---:|---|
| chat | 8k | 普通多轮对话、闲聊 |
| rag | 16k～32k | 常规知识库问答 |
| long_context | 64k～128k | 跨多文档/长历史回顾 |
| max_context | 不超过 280k | 明确的长上下文任务，预留系统和输出空间 |

不要把 `300000` 直接写成每轮 `total_budget`。运行时必须保留 `SYSTEM_RESERVE + OUTPUT_RESERVE`，并记录实际输入 token、输出 token、延迟和成本。后续要增加“长上下文触发原因”和用户可见的加载范围。

## 6. 当前模型与调用分工

当前所有会话理解、摘要、记忆选择、更新计划、回答和验证都使用 `deepseek-v4-flash` 成本策略。调用分工应保持窄职责：

```text
rewrite       只改写问题并生成 working memory
selection     只从候选 memory_id 中选择
generation    只依据证据/上下文生成答案
verification  只检查 grounded/useful/引用覆盖
memory update 只生成计划，不直接写数据库
```

每次调用都必须有结构化 JSON schema、超时、重试和 deterministic fallback。模型输出不是权限边界，数据库服务才是最终边界。

## 7. ReAct 与当前 LangGraph 的关系

当前状态图不是完整 ReAct Agent，而是固定路由的有界 RAG workflow。目标重构为 LangGraph 承载的受控 ReAct Runtime：知识库检索和联网搜索通过 Tool Gateway 执行，工具结果规范化为 Observation，Agent 再决定回答、继续调用、澄清或拒答。

记忆模块在新架构中保持独立职责：初始化时加载三层上下文，循环中只更新 request-scoped working memory，最终提交阶段才更新 session summary 和 long-term memory。详细协议见 [ReAct 运行时与工具协议](react-agent/ReAct运行时与工具协议.md)。

实现时 ReAct 只能通过 Tool Gateway 调用工具，不能直接让模型任意执行 MCP/Skill。必须限制工具白名单、最大步数、超时、用户权限、幂等键和审计字段。

## 8. 可观测性和测试

每轮 trace 至少记录：

```text
memory_load_ms / memory_update_ms
working_memory schema_version
summary_version_before/after
long_term_candidate_ids / selected_memory_ids
expired_or_stale_memory_count
loaded/omitted/missing sections
input/output tokens and estimated cost
summary update reason
memory actions and idempotency result
```

必须覆盖以下测试：

1. request 工作记忆不会跨请求或跨会话泄漏。
2. user/project scope、用户隔离和分支隔离。
3. expires_at、valid_to、stale、supersede、deleted tombstone。
4. 用户纠正旧事实后新事实优先，旧事实可审计。
5. 摘要游标和版本冲突不会倒退或覆盖新结论。
6. 长上下文预算会保留必选区块并记录裁剪。
7. `E#` 证据和 `MEM#` 记忆不会混淆，记忆不能生成引用。
8. request_id 重试不会重复写消息、摘要或长期记忆。

## 9. 实施顺序

1. 先更新 schema、Prompt section 名称和文档，保持旧字段兼容。
2. 将工作记忆扩展为 `wm.v1`，补充 `goal/working_plan/current_focus`。
3. 为长期记忆增加 freshness/valid-time 计算、stale 扫描和 tombstone 约束。
4. 引入可选向量召回，保留关键词回退，记录候选评分组成。
5. 将上下文预算改成 chat/rag/long_context/max_context 分档，并补充长历史 recall。
6. 通过离线记忆评测集验证“该记忆是否应该加载/写入/过期/替换”，再扩大自动写入范围。
