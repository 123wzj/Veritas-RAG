问题分析：
- 这不是单纯的“没搜到 OpenAI 新闻”，而是复合问题在当前 graph 中只做了一次整体路由，没做到按子问题独立执行。
- `backend/graph/nodes/query_nodes.py` 的 `decompose_query` 虽然会产出 `sub_questions` 和 `retrieval_queries`，但后续节点没有把这些子问题当作独立任务分别处理。
- `backend/graph/nodes/retrieval_nodes.py` -> `backend/services/retrieval/hybrid.py` 这一段能够消费 `retrieval_queries`，说明知识库检索支持多 query 变体融合。
- 但 `backend/graph/nodes/web_nodes.py` 当前只使用 `query_rewritten` 或原始 `query` 做一次联网搜索，没有消费 `sub_questions` / `retrieval_queries`，所以复合时事问题在联网阶段容易只覆盖其中一个子问题。
- `backend/graph/nodes/retrieval_nodes.py` 的 `judge_evidence` 是对整条问题做一次整体覆盖度判断，不是按子问题逐项判断；只要部分证据足够，就可能让另一个子问题直接落入“证据不足”。
- `backend/graph/nodes/generation_nodes.py` 也是按整体问题生成答案，没有强约束模型“逐个子问题回答并逐项引用”，所以更容易出现“杭州天气回答完整，但 OpenAI 部分只能说证据不足”的现象。

涉及链路：
- `backend/api/v1/endpoints/rag.py`
- `backend/graph/graph.py`
- `backend/graph/nodes/query_nodes.py`
- `backend/graph/nodes/web_nodes.py`
- `backend/graph/nodes/retrieval_nodes.py`
- `backend/graph/nodes/generation_nodes.py`
- `backend/graph/nodes/reflection_nodes.py`

结论：
- 这是查询路由问题，但不只是“route_type 判错”这么简单。
- 更准确地说，是“整体级路由 + 单 query 联网搜索 + 整体级证据评估/生成”共同导致了复合问题只能覆盖第一个子问题。
- 当前最值得优先修复的点是 `backend/graph/nodes/web_nodes.py`，因为它没有按 `sub_questions` / `retrieval_queries` 分别联网搜索。

修复方案：
1. 最小修复（优先做）
   - 修改 `backend/graph/nodes/web_nodes.py`
   - 联网搜索优先遍历 `sub_questions`，其次 `retrieval_queries`，最后回退到 `query_rewritten` / `query`
   - 每个 query 单独搜索，再把结果合并、去重、统一编号后回写到 `selected_evidence`

2. 证据评估增强
   - 修改 `backend/graph/nodes/retrieval_nodes.py` 的 `judge_evidence`
   - 从“整条问题一个 coverage_score”改成“按 sub_question 判断 coverage”
   - 只要还有未覆盖的子问题，并且允许联网，就继续触发 `web_search` 或 `reflection`

3. 生成阶段约束
   - 修改 `backend/graph/nodes/generation_nodes.py`
   - prompt 中明确要求按子问题分段回答、分别引用
   - 如果某个子问题证据不足，要单独说明不足，避免一个子问题的证据覆盖掉另一个子问题

4. 长期方案
   - 把当前“整条 query 一次 route”的模式升级为“每个 sub_question 独立 route / 检索 / 聚合”
   - 这样才能同时支持：一个子问题走知识库，另一个子问题走联网搜索，最后再统一汇总成一个答案


具体分析

  1. 入口层没问题，问题在 graph 后段

  RAG 入口只是把整条 query 丢进 graph：

  - backend/api/v1/endpoints/rag.py:136
  - backend/api/v1/endpoints/rag.py:262

  这里没有对子问题做单独执行，属于正常入口。

  ---
  2. decompose_query 只是“产出子问题”，但没有真正变成多路执行

  关键位置：

  - backend/graph/nodes/query_nodes.py:159
  - backend/graph/nodes/query_nodes.py:173
  - backend/graph/nodes/query_nodes.py:216

  这里做了两件事：

  - 识别复合问题
  - 产出：
    - sub_questions
    - retrieval_queries

  问题是：
  这些子问题只是被放进状态里，没有被当作独立子任务执行。

  也就是说，系统不是：

  - 子问题 A 单独路由/单独搜
  - 子问题 B 单独路由/单独搜

  而是：

  - 整体 query 只路由一次
  - 后续节点消费一个共享状态

  这就是第一个结构性问题。

  ---
  3. 路由是“单一路由”，不是“按子问题路由”

  关键位置：

  - backend/graph/nodes/query_nodes.py:240
  - backend/graph/nodes/query_nodes.py:251
  - backend/graph/nodes/query_nodes.py:295
  - backend/graph/nodes/query_nodes.py:336

  这里的 plan_query_route 只输出一个：

  - route_type
  - need_retrieval
  - need_web_search

  对整个请求只做一次判定。

  这会带来的问题

  一个复合问题里可能同时包含：

  - 子问题 A：时效性天气 -> 应该 web/hybrid
  - 子问题 B：OpenAI 最近新闻 -> 也应该 web/hybrid
  - 另一些问题甚至可能是：
    - 一个问知识库
    - 一个问时事

  但当前状态机只允许一个总路由。

  所以它不能表达：

  - 子问题1 走 web
  - 子问题2 再走 web
  - 或子问题1 走 KB，子问题2 走 web

  这说明路由粒度过粗。

  ---
  4. KB 检索支持多 query，但 web_search 只搜一个主 query

  这是最关键的落差。

  KB 检索

  retrieve_hybrid 会读取：

  - retrieval_queries
  - backend/graph/nodes/retrieval_nodes.py:50
  - backend/graph/nodes/retrieval_nodes.py:57

  而 hybrid.py 里也确实会对多个 variant 执行：

  - backend/services/retrieval/hybrid.py:81
  - backend/services/retrieval/hybrid.py:86
  - backend/services/retrieval/hybrid.py:112

  也就是说：
  知识库检索是支持多查询变体融合的。

  但 web_search 不支持

  web_nodes.py 这里直接只取：

  - query_rewritten 或原 query
  - backend/graph/nodes/web_nodes.py:25

  然后只做一次：

  - search_with_snippets(query=query, max_results=5)
  - backend/graph/nodes/web_nodes.py:39

  这意味着即使前面拆出了多个子问题，到了 web search 阶段也只搜一个主查询。

  对于你这个例子，非常可能发生：

  - 主 query 改写/模型理解偏向“杭州天气”
  - 搜索结果几乎全是天气
  - OpenAI 最近大事情 没有单独搜索机会

  这和你在 docs/问题记录.md 里看到的现象完全一致。

  ---
  5. hybrid 路由并不会“自动先 KB 再 web 全覆盖子问题”

  在代码里：

  - route_type == "hybrid" 时
  - need_retrieval = kb_id is not None
  - need_web_search = False
  - backend/graph/nodes/query_nodes.py:308

  也就是说 hybrid 不是“同时双路跑”，而是：

  - 先检索
  - 后面看证据评审是否不足
  - 再决定要不要 web

  而证据评审是针对整体问题做的，不是按子问题做 coverage。

  ---
  6. 证据评审没有强约束“每个子问题都必须被覆盖”

  关键位置：

  - backend/graph/nodes/retrieval_nodes.py:167
  - backend/graph/nodes/retrieval_nodes.py:217

  虽然 prompt 里把 sub_questions 传给了评审器：

  - 子问题：{sub_questions or "无"}

  但实际决策只有一个总结果：

  - coverage_score
  - answerability_score
  - recommended_action

  然后给出整体布尔值：

  - evidence_sufficient
  - need_reflection
  - need_web_search

  问题在于这不是“per-sub-question coverage”。

  所以只要模型觉得：
  - 杭州天气这部分证据挺充分
  - OpenAI 那部分没有

  它也可能给出“部分可答 + 部分不足”的整体判断，而不是强制继续为第二个子问题补证据。

  ---
  7. 生成阶段也没有“按子问题逐项作答”的硬约束

  关键位置：

  - backend/graph/nodes/generation_nodes.py:162
  - backend/graph/nodes/generation_nodes.py:178

  生成 prompt 里传的是：

  - 原始问题
  - 路由类型
  - 一批 selected_evidence

  但没有要求模型：

  - 先列出每个子问题
  - 判断每个子问题是否有证据
  - 对每个子问题分别回答并分别引用

  所以它自然会按“整体问题”自由组织回答。
  这就会出现你记录里的表现：

  - 杭州天气答得比较完整
  - OpenAI 部分说“当前没有证据”

  从系统角度看，这其实是“合理但不理想”的行为。

  ---
  根因判断

  是不是查询路由有问题？

  是，但不只是路由问题。

  更准确地说是三个问题叠加：

  1. 路由粒度错误

  - 当前是“整条 query 一个 route”
  - 不是“每个 sub_question 一个 route”

  2. web_search 没有消费 retrieval_queries / sub_questions

  - KB 检索支持多 query
  - web_search 只搜单 query
  - 这是造成时事复合问题覆盖不全的直接原因

  3. 证据评审与生成都不是按子问题对齐

  - 没有逐个子问题检查 coverage
  - 没有逐个子问题生成答案
