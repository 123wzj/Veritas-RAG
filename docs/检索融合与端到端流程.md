# 检索融合与端到端流程



```python
RETRIEVAL_CONFIG = {
    # chunking
    "parent_chunk_size": 1200,
    "child_chunk_size": 300,
    "child_overlap": 60,
    "sibling_window": 1,

    # retrieval
    "final_top_k": 6,
    "dense_top_k": 100,
    "sparse_top_k": 100,

    # fusion
    "rrf_k": 60,
    "dense_weight": 1.0,
    "sparse_weight": 0.9,
    "fusion_top_k": 50,

    # rerank
    "rerank_input_k": 40,
    "rerank_keep_k": 12,

    # evidence packing
    "final_evidence_k": 6,
    "max_evidence_tokens": 6000,
    "max_evidence_per_parent": 2

```



## 1. 文档目标

这份文档说明当前项目最新的检索融合方案，以及从文档入库到用户提问、召回、融合、精排、父块回补、生成答案的完整链路。

```text
Dense 独立召回
Sparse 独立召回
-> Weighted RRF 融合
-> MySQL 父块回补
-> Reranker 精排
-> Evidence Packing
-> Evidence Grading / Reflection
-> 答案生成与验证
```

注意：当前 sparse 不是“在 dense 候选里做二次打分”，而是应用层独立 first-stage recall。

---

## 2. 当前检索结构

当前检索层入口：

- `backend/services/retrieval/hybrid.py`
- `backend/services/retrieval/reranker.py`
- `backend/embeddings/embeddings.py`
- `backend/embeddings/sparse.py`

当前真实主流程不是“先 dense，再在 dense 候选里做 sparse 重排”，而是：

```text
query / query_variants
  -> 为每个 query variant 并发执行 dense recall + sparse recall
  -> 把多 query、多通道结果一起做 weighted RRF fusion
  -> 对 RRF top candidates 做 parent backfill
  -> 把 backfilled candidates 交给 reranker
  -> 取 reranker top results 进入 evidence packing
```

### 2.1 入库阶段如何为检索做准备

实现位置：

- `backend/services/ingestion/ingestion.py`
- `backend/models/database/knowledge.py`

当前入库阶段会对每个 child chunk 同时构建两种表示：

1. dense vector
2. sparse vector

具体做法：

- `child_dense_vectors = self.embeddings.embed_documents(child_texts)`
- `child_sparse_vectors = self.sparse_embeddings.embed_documents(child_texts)`

然后分别写入不同存储：

#### Dense 存储

- 写入 Chroma
- 只存 child chunk 的 dense 向量
- 同时写入轻量检索元数据：
  - `kb_id`
  - `doc_id`
  - `parent_id`
  - `chunk_id`
  - `is_parent=false`
  - `modality`
  - `language`
  - `title`
  - `section_path`
  - `page_no`
  - `token_count`
  - `lexical_terms`（仅调试/回溯用）

#### Sparse 存储

- 写入 MySQL `chunks.sparse_vector`
- 只给 child chunk 保存 sparse vector
- parent chunk 不参与 first-stage recall

这意味着当前项目是：

- Chroma 负责 dense recall
- MySQL 负责 child 正文、parent 正文、以及 sparse vector 持久化

## 3. Dense 召回是怎么做的

实现位置：

- `backend/services/retrieval/hybrid.py -> _dense_retrieve_async`
- `backend/embeddings/embeddings.py -> BGEM3EmbeddingsAdapter`
- `backend/embeddings/bge_m3.py`

### 3.1 Dense 使用什么模型

当前默认 dense embedding provider 是：

- `BGE-M3`

代码路径：

- `backend/embeddings/embeddings.py`
- `backend/embeddings/bge_m3.py`

实际调用链：

```text
get_embeddings()
  -> BGEM3EmbeddingsAdapter
  -> get_bge_m3_encoder()
  -> BGEM3FlagModel
```

其中 `BGEM3Encoder` 做了几件事：

- 使用单例缓存模型
- 通过 `threading.RLock()` 保证 encode 时线程安全
- 在 CUDA 可用时可启用 fp16
- 对文本做规范化：空文本替换成 `[EMPTY]`

### 3.2 Dense是怎么编码的

这些 embedding 模型通常是 **bi-encoder / sentence transformer** 架构：文本先经过 Transformer，再通过 pooling 得到一个句向量或段落向量，用于后续相似度计算。

### 3.3 Dense 是怎么查 Chroma 的

查 Chroma 时只查 child chunk：

```python
collection.query(
    query_embeddings=[query_vector],
    n_results=limit,
    where={"$and": [{"kb_id": kb_id}, {"is_parent": False}, ...]},
    include=["metadatas", "distances"],
)
```

核心过滤条件：

- `kb_id == 当前知识库`
- `is_parent == False`
- 如果有模态约束，还会加 `modality`

### 3.4 Dense 的原始分数怎么得到

Chroma 返回的是 `distance`，当前项目把它转成一个便于统一处理的相似分数：

```text
score = 1 / (1 + distance)
```

文档预处理阶段：把所有子块 embedding 建索引

查询阶段：把 query 也编码成向量

在索引里找与 query 向量最接近的 topK 子块

### 3.5 Dense 召回后为什么还要 hydrate

Chroma 里没有保存 child 正文，所以 dense 召回完只拿到了：

- chunk_id
- metadata
- score

接着 `_hydrate_child_results_sync` 会去 MySQL `chunks` 表里按 `chunk_id` 把 child 正文补回来，补充字段包括：

- `content`
- `title`
- `section_path`
- `page_no`
- `doc_id`
- `token_count`
- `language`
- `parent_id`

所以当前 dense recall 的真实结果不是“只有向量库 metadata”，而是“向量召回 + MySQL child hydration”后的候选。

### 3.6 Dense 召回的候选规模

在 `retrieve_async` 里，每个 query variant 的 dense limit 是：

```text
max(desired_top_k * 5, self.dense_top_k // 2)
```

其中：

- `desired_top_k = max(6, min(top_k or rerank_top_k, 20))`
- 默认 `dense_top_k = 40`

所以 dense first-stage recall 会故意放大召回池，再交给 RRF 和 reranker 逐层收缩。

## 4. Sparse 召回是怎么做的

实现位置：

- `backend/services/retrieval/hybrid.py -> _sparse_retrieve_async`
- `backend/services/retrieval/hybrid.py -> _load_sparse_corpus_sync`
- `backend/embeddings/sparse.py`

### 4.1 BM25 和 learned sparse 的区别与联系

联系：它们都保留了“词项维度”的思想

BM25 和 learned sparse 的共同点是：

- 都不是 dense embedding 那种“384/768 维稠密语义向量”
- 都更接近“词项空间”上的表示
- 都可以利用倒排索引或类似 posting list 的检索结构
- 都比较擅长关键词、术语、实体名、缩写、代码符号这类精确匹配

Qdrant 对 sparse vectors 的解释就是：每个维度可以对应某个词或子词，非零维很少，因此可解释性强，也适合高效检索。Sentence Transformers 也把 sparse encoder 定义为输出“多数维度为零的 sparse embeddings”，并强调它与 dense embeddings 是互补的。

所以从“大类”上说：

- **BM25 是经典词项统计型 sparse retrieval**
- **learned sparse 是神经网络学习出来的 sparse retrieval**

区别：BM25 的权重来自统计规则，learned sparse 的权重来自模型学习

这是两者最本质的差异。

BM25 的分数来自人工定义好的统计公式，主要依赖：

- term frequency
- inverse document frequency
- document length normalization

也就是说，权重是**规则算出来的**，不是模型学出来的。Elastic 的 BM25 文档就是这样定义的。



learned sparse 则是把文本送入一个模型，让模型决定：

- 哪些词项维度应该激活
- 每个激活维度应该给多大权重

Sentence Transformers 对 SparseEncoder 的定义就是：它把文本映射成 sparse embeddings；Qdrant 对 SPLADE 的介绍则说明，像 SPLADE 这类方法会生成高效、可解释的 sparse vectors，用于检索任务。

所以一句话概括：

- **BM25：统计驱动**
- **learned sparse：模型驱动**



两者的另一个关键区别：query expansion / semantic generalization 能力

BM25 基本只会“你 query 里出现了什么词，我就按这些词去找”。
 它强在精确术语命中，但弱在语义改写。

learned sparse，尤其像 SPLADE 这类方法，可以通过模型把文本映射到更多有意义的词项维度上，因此常常具有某种程度的**语义扩展能力**。Qdrant 在 SPLADE 说明里明确提到它是 learned sparse representation；现代 sparse neural retrieval 文章也把这类方法归为神经稀疏检索。



#### learned sparse 到底是怎么做的

你可以把它理解成：
 **模型输出一个“高维但绝大多数位置为 0”的向量，非零位置对应某些词/子词特征，值表示这些特征的重要性。**

虽然 learned sparse 是模型生成的，但它仍然保留了“稀疏项检索”的可索引性。

也就是说，子块经过模型后，只激活少量 token dimensions；这些非零维就可以像倒排项一样建立检索结构。

### 4.2 Sparse 的文档是怎么准备的

在 `_load_sparse_corpus_sync` 里，系统会：

1. 从 MySQL `chunks` 表加载当前知识库全部 child chunk：**把“知识库里全部子块”作为 BM25 的 document 集合统一建索引**
2. 只取 `is_parent=false` 的行
3. 如果指定了 `modality`，再按模态过滤
4. 对缺失 `sparse_vector` 的 chunk 动态回填并写回数据库

动态回填逻辑：

```text
如果 row.sparse_vector 为空，且 row.content 非空
  -> self.sparse_embedding.embed_documents(texts)
  -> 写回 row.sparse_vector
  -> db.commit()
```

所以 sparse vector 既会在入库阶段写入，也支持在检索阶段兜底补齐。

### 4.3 Sparse 的分词与编码方式

`BM25Encoder.tokenize()` 做的事情：

#### 英文/数字 token

用正则提取：

```text
[a-z0-9][a-z0-9_\-.+#/]*
```

这类 token 很适合保留：

- API 名
- 字段名
- 路径
- 版本号
- 错误码
- 带符号标识符

#### 中文 token

- 优先使用 `jieba.lcut`
- 如果没装 `jieba`，退化为中文连续片段正则

#### 最终 sparse vector

对 token 做词频统计：

```text
{
  token -> term frequency,
  __doc_len__ -> 文档长度
}
```

这里的 `__doc_len__` 会被后续 BM25 评分用来做长度归一化。

### 4.4 Sparse query 是怎么编码的

- 分析 query，得到若干 query terms
- 去倒排表里找这些词出现在哪些子块
- 根据 BM25 公式对这些子块打分
- 返回 topK 子块

所以你可以把 BM25 理解成：

**子块级 document 集合 + 倒排索引 + BM25 打分函数**

### 4.5 Sparse 的 corpus stats 怎么计算

在真正打分前，系统会针对当前知识库的 child corpus 重新计算一套 corpus-level stats：

- `doc_count`
- `idf`
- `avg_doc_len`

IDF 公式是：

```text
idf(token) = log(1 + (N - df + 0.5) / (df + 0.5))
```

其中：

- `N` 是当前知识库 child chunk 总数
- `df` 是该 token 出现于多少个 child chunk

### 4.6 Sparse 的打分公式

当前 `_sparse_score()` 会调用 `SparseEmbedding.score()`，而其内部是标准 BM25 风格公式：

```text
term_score = idf * ((tf * (k1 + 1)) / (tf + k1 * (1 - b + b * doc_len / avg_doc_len)))
```

默认参数：

- `k1 = 1.5`
- `b = 0.75`

然后项目还加了一个 token boost：

- token 长度 >= 4：`+0.15`
- token 含数字：`+0.1`
- token 同时含字母和数字：`+0.15`

最终单 token 贡献会乘上：

- `token_boost(token)`
- `max(query_weight, 1.0)`

所以当前 sparse 不只是“朴素 BM25”，而是“BM25 + 技术标识符增强”的版本。

### 4.7 Sparse 为什么适合技术知识库

这套 sparse 对下列内容会更敏感：

- 字段名
- 方法名
- API 路径
- chunk_id / parent_id / is_parent 这类精确术语
- 带数字的型号、版本、错误码

这正是 dense 容易漏掉、但企业文档里又很常见的部分。

### 4.8 Sparse 召回结果怎么返回

对整个 child corpus 算完 lexical score 后：

- 过滤 `score <= 0` 的文档
- 按 score 降序排序
- 取 top `limit`

每条 sparse result 会附带：

- `score`
- `retrieval_type = "sparse"`
- `content`
- `title`
- `section_path`
- `page_no`
- `doc_id`
- `parent_id`
- `sparse_vector`

## 5. 多 Query 检索是怎么做的

实现位置：

- `backend/services/retrieval/hybrid.py -> _build_query_plan`

当前不是只拿一个 query 检索，而是把：

- 原始 query
- rewrite query
- decomposition 产出的 retrieval queries

一起纳入计划。

### 5.1 Query 去重

所有 query variant 先做：

- 去首尾空格
- 多空格压缩
- lower-case 去重

### 5.2 最多保留多少个 query

最多保留前 4 个 query variant。

### 5.3 Query 权重怎么给

当前实现：

- 第 1 个 query：`1.0`
- 第 2 个 query：`0.9`
- 第 3 个 query：`0.65`
- 第 4 个 query：`0.55`

更准确地说，后两个的规则是：

```text
weight = max(0.5, 0.85 - idx * 0.1)
```

其中 `idx` 从 0 开始。

这意味着：

- 主 query 权重最高
- rewrite query 次之
- 额外扩展 query 仍有贡献，但会被适度压低

### 5.4 每个 query variant 怎么执行

对每个 `(variant, weight)`，系统会并发执行：

- dense recall
- sparse recall

然后把 `match_query` 和 `query_weight` 记到每条结果里，供后续 RRF 使用。

## 6. RRF 是怎么做的

实现位置：

- `backend/services/retrieval/hybrid.py -> _fuse_multi_query_results`

当前实现不是简单 RRF，而是：

- 多 query
- 多检索器
- 带 retrieval weight
- 带 query weight

的 weighted RRF。

### 6.1 为什么这里不用直接拼 score

因为这里同时混合了：

- dense score
- sparse score
- 不同 query variant 的结果

这几路分数的尺度都不一致：

- dense score 来自 `1 / (1 + distance)`
- sparse score 来自 BM25 风格 lexical score
- 多 query 之间也没有天然可比性

所以当前项目完全不尝试对原始分数做统一归一化后线性加权，而是只使用“排序位置”做融合。

### 6.2 RRF 的核心公式

当前代码里的加分公式：

```text
weighted_rrf = retrieval_weight * query_weight / (k + rank + 1)
```

其中：

- `k = 60`
- `rank` 从 0 开始
- `query_weight` 来自 query plan
- `retrieval_weight`：
  - dense = `1.0`
  - sparse = `0.9`

### 6.3 这意味着什么

如果某个 chunk：

- 在主 query 的 dense 结果里排得很靠前
- 同时在 rewrite query 的 sparse 结果里也排得不错

那么它会从多条列表累加分数，最终 `rrf_score` 就会更高。

也就是说，当前 RRF 奖励的是：

- 多路都命中
- 且每一路排名都不错

而不是单一路径分数特别大。

### 6.4 Dense 和 Sparse 的相对权重

当前 dense 略高于 sparse：

- dense `retrieval_weight = 1.0`
- sparse `retrieval_weight = 0.9`

这表示系统偏向：

- 语义召回优先
- 但 lexical 命中仍然有很强的话语权

### 6.5 多路结果去重是怎么做的

`merged` 以 `chunk_id` 为键合并。

合并规则：

- 第一次出现：直接记录
- 后续重复出现：
  - `score` 取更大的那个原始 score
  - `match_query` 保留已有值或补入新值
  - 如果 dense/sparse 混合命中，则 `retrieval_type = "hybrid"`

最后给每个 chunk 写入：

- `rrf_score`

然后按 `rrf_score` 降序排序。

### 6.6 为什么 RRF 放在 reranker 前面

因为 RRF 的职责是：

- 把多 query、多通道 first-stage recall 融成一个更稳的粗排候选池

而 reranker 的职责是：

- 在更小的候选池里做更精细的 pairwise / cross-encoder 相关性判断

所以两者不是替代关系，而是两层不同粒度的排序。

## 7. 父块回补

实现位置：

- `backend/services/retrieval/hybrid.py -> _parent_backfill_sync`

当前架构中，父块正文不再依赖 Chroma，而是从 MySQL 查询。

流程：

1. Dense / Sparse 都只召回 child chunk
2. RRF 融合后先截取前一批 child candidates
3. 提取候选里的 `parent_id`
4. 按 `parent_id` 去重
5. 到 MySQL `chunks` 表中查 `is_parent=true` 的父块
6. 把父块内容补成：
   - `parent_content`
   - `parent_title`
   - `parent_section_path`
   - `parent_page_no`
   - `parent_token_count`

这样做的原因：

- child chunk 适合 first-stage recall
- parent chunk 更适合最终回答和 rerank 判断
- MySQL 更适合存正文和结构化元数据

### 7.1 回补后会保留多少候选

在 `retrieve_async` 里：

- 先对 `fused_results[: desired_top_k * 4]` 做父块回补
- 最后返回 `backfilled_results[: desired_top_k * 3]`

也就是说，进入 reranker 的是一个经过放大召回、RRF 融合、父块回补后的中间候选池。

## 8. Reranker 是怎么做的

实现位置：

- `backend/services/retrieval/reranker.py`
- `backend/graph/nodes/retrieval_nodes.py -> rerank_candidates`

### 8.1 当前默认 reranker 模型

默认 provider 是：

- `bge`

默认模型是：

- `BAAI/bge-reranker-v2-m3`

实际封装类：

- `BGEReranker`

底层使用：

- `FlagEmbedding.FlagReranker`

### 8.2 Reranker 输入什么

reranker 输入不是原始 child chunk，而是“经过 parent backfill 的候选文档”。

`_prepare_document()` 会优先拼装：

1. `parent_content`
2. `child content`
3. `parent_title / title`
4. `parent_section_path / section_path`

具体规则：

- 优先用 `parent_content`
- 如果没有 `parent_content`，退回 `child content`
- 如果有标题/章节路径且正文里还没体现，就把它们作为 header 拼到最前面
- 如果 parent_text 存在，且 child_text 不在 parent_text 中，再补一个 `Child snippet`
- 最终文档文本截断到 `6000` 字符

query 本身也会做：

- 空白规范化
- 截断到 `2000` 字符

### 8.3 Reranker 真正怎么打分

构造的输入对是：

```text
[query, prepared_document]
```

然后调用：

```python
self.model.compute_score(pairs, batch_size=self.batch_size, normalize=True)
```

这里的关键点：

- 它不是 embedding cosine，而是 reranker 模型直接做相关性打分
- `normalize=True`，所以会得到归一化后的分数
- 每条候选写入 `rerank_score`
- 再按 `rerank_score` 降序排序

### 8.4 Reranker 取多少条

在 graph 节点 `rerank_candidates()` 里，每个子问题会调用：

```text
top_k = max(state.top_k * 2, 8)
```

如果默认 `state.top_k = 6`，那 reranker 默认会保留：

- `12` 条

之后 `pack_evidence()` 再继续去重和截断成最终 evidence。

### 8.5 如果 reranker 失败怎么办

当前有兜底逻辑：

- 如果 rerank 抛异常，就直接取 `retrieved_docs[: max(top_k * 2, 8)]`

所以 reranker 是增强层，不会让整个链路因为模型问题彻底中断。

### 8.6 当前还有一个 SimpleReranker

项目里还保留了：

- `SimpleReranker`

它的逻辑是：

- 对 query 分词
- 看词是否命中标题和正文
- 标题命中权重更高

但它只是 fallback provider，当前默认主路径仍然是 `BGE reranker`。

## 9. RRF 和 Reranker 的关系

最容易混淆的一点是：

- RRF 不是 reranker
- reranker 也不是 RRF 的替代品

它们解决的是两个不同层级的问题。

### 9.1 RRF 解决什么问题

RRF 解决的是：

- 多 query 怎么合并
- dense 和 sparse 怎么合并
- 原始分数尺度不统一怎么办

所以它属于：

- first-stage recall 之后的融合粗排

### 9.2 Reranker 解决什么问题

reranker 解决的是：

- 在已经比较相关的一批候选里，谁最适合回答当前 query
- 哪些候选虽然能召回，但其实上下文不完整或不够贴题

所以它属于：

- second-stage 精排

### 9.3 当前项目为什么两者都要

因为当前项目要同时兼顾：

- 语义召回
- 关键词召回
- 多 query 扩展
- 最终回答上下文质量

如果只有 RRF：

- 能融合多路结果
- 但不能替代真正的 cross-encoder 精排

如果只有 reranker：

- 需要先有足够好的候选池
- 否则根本没有机会看到那些被 dense 或 sparse 漏召回的文档

所以当前设计是：

```text
Dense / Sparse first-stage recall
  -> Weighted RRF 做融合粗排
  -> Parent backfill
  -> Reranker 做精排
  -> Evidence packing
```

这也是当前项目检索链路最核心的设计。

## 10. 从文档入库到回答的完整流程

### 10.1 入库流程

```text
上传文件
  -> 保存原始文件到 data/uploads/<user_id>/<kb_id>/
  -> 文档解析
  -> 生成 parent chunks
  -> 生成 child chunks
  -> 对 child chunks 做 dense / sparse 表示构建
  -> child dense vector + metadata 写入 Chroma
  -> parent / child 正文写入 MySQL chunks
  -> documents 表记录文档状态
```

核心存储原则：

- Chroma 只做子块向量检索
- MySQL 存父子块正文

### 10.2 查询流程

```text
用户提问
  -> 加载记忆
  -> Query Rewrite
  -> Query Decomposition
  -> 生成 sub_query_plans
  -> 按子问题 Route Planning
      -> chat: 直接回答
      -> web_search: 联网搜索
      -> knowledge_base: 知识库检索
      -> hybrid: 知识库优先，必要时联网补充
  -> 按子问题 Dense 子块召回
  -> 按子问题 Sparse 子块召回
  -> Weighted RRF 融合
  -> MySQL 父块回补
  -> Reranker 精排
  -> Per-sub-question Evidence Packing
  -> Per-sub-question Evidence Grading
  -> Reflection，最多 3 次，到上限后收口
  -> Per-sub-question 答案生成
  -> 答案聚合
  -> Answer Verification
  -> 返回答案和 citations
```

---

## 11. 当前方案优点

- 检索粒度清晰：子块召回，父块生成
- 存储职责清晰：Chroma 检索，MySQL 正文和业务数据
- 召回更稳：Dense 解决语义，Sparse 解决关键词
- 融合更稳：RRF 避免不同分数尺度难以比较
- Agent 更智能：路由规划、证据判断、反思和验证组成闭环
- 流程更稳：Reflection 到上限后会收口，不会因为证据不足无限重试
- 复合问题覆盖更完整：每个子问题都能独立检索、联网、评审和生成
- 引用更可追溯：证据统一编号为 `E#`

---

## 12. 当前边界

当前 sparse 是应用层 lexical sparse recall，不是 Chroma 原生 sparse index。  
对当前学习型项目和中小规模知识库足够合适；如果未来知识库规模变大，可以考虑：

- 引入专门的 BM25 / Elasticsearch 检索通道
- 使用支持原生 hybrid search 的向量数据库
- 引入 learned sparse 或 late interaction retrieval

---

## 13. 面试表达

可以这样说：

> 我没有把 sparse 做成 dense 候选里的重排，而是把它做成独立召回通道。Dense 从 Chroma 召回语义相关子块，Sparse 从 MySQL 的 child corpus 召回关键词相关子块，两路结果再用 Weighted RRF 融合。融合后根据 parent_id 到 MySQL 回补父块，再交给 Reranker 精排。这样既能补召回，也能保证生成阶段上下文完整。
