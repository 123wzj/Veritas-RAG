# Agentic RAG 模块与方法说明

## 1. 文档目标

这份文档聚焦“模块”和“方法”两个维度，说明当前项目里每个核心模块：

- 用了什么方法
- 为什么选这种方法
- 主要解决什么问题

本文只对应当前最新实现，不再描述旧的 Milvus 版本。

---

## 2. 整体方法总览

当前 Agentic RAG 主链路可以概括为：

```text
文档上传
  -> 文档解析
  -> Parent-Child 分块
  -> 子块 dense / sparse 表示构建
  -> 子块向量 + 元数据写入 Chroma
  -> 父块和子块正文写入 MySQL

用户提问
  -> 加载用户记忆
  -> Query Rewrite
  -> Query Decomposition
  -> 生成 sub_query_plans
  -> 按子问题 Route Planning
      -> chat
      -> web_search
      -> knowledge_base
      -> hybrid
  -> 按子问题 Dense 子块召回
  -> 按子问题 Sparse 子块召回
  -> Weighted RRF 融合
  -> 父块回补
  -> Rerank 精排
  -> Per-sub-question Evidence Packing
  -> Per-sub-question Evidence Grading
  -> Reflection（最多 3 次）
  -> Per-sub-question 答案生成
  -> 答案聚合
  -> 事实校验
  -> 写入记忆
```

## 3. 模块总表

| 模块 | 当前方法 | 为什么选这种方法 | 解决的问题 |
|------|----------|------------------|------------|
| 文档解析 | 多格式统一解析 | 先把 PDF、DOCX、Markdown 等统一成结构化文本 | 解决不同格式文档无法共用同一套入库逻辑 |
| 分块 | Parent-Child Chunking | 检索精度和回答上下文需要分开处理 | 解决小块上下文不足、大块召回不准 |
| 向量化 | 子块 Dense + Sparse 双表示 | 语义召回和关键词命中都很重要 | 解决 Dense 忽略术语、Sparse 不懂语义 |
| LLM / 模型接入 | OpenAI-compatible LLM + 本地 BGE Embedding / Reranker | 推理模型与检索模型职责分离，更便于独立替换 | 解决问答生成、召回、精排混在一起难调优 |
| 向量存储 | Chroma 仅存子块向量和检索元数据 | 向量库只负责 first-stage recall | 让检索库更轻、更纯粹 |
| 正文存储 | MySQL 存父子块正文 | 父块回补和结构化正文更适合关系库 | 解决长正文不适合长期堆在向量库 |
| 查询理解 | Rewrite + Decomposition | 用户问题经常口语化、复杂化 | 提高复杂问题的检索覆盖 |
| 路由规划 | Chat / Web / KB / Hybrid | 不是所有问题都该走同一条链路 | 让系统更像智能体，而不是固定检索器 |
| 检索召回 | Dense Recall + Independent Sparse Recall | 两路召回互补 | 降低单一路径漏召回 |
| 检索融合 | Weighted RRF | 不同检索器分数难直接比较 | 稳定融合 Dense/Sparse 和多 Query 结果 |
| 父块回补 | 按 parent_id 去 MySQL 查父块 | 检索结果和生成上下文职责分离 | 让回答拿到完整上下文 |
| 精排 | Reranker | 召回到不等于最适合回答 | 提高最终上下文质量 |
| 证据管理 | Evidence Packing + Evidence ID | 后续生成和验证都要围绕证据对象工作 | 让引用、验证、日志统一 |
| Agent 控制 | Evidence Grading + Reflection | 系统需要知道何时继续找证据 | 解决“没证据也硬答” |
| 联网增强 | Web Search 作为补充证据 | 有些问题天然依赖实时信息 | 解决知识库内没有最新信息 |
| 权限与会话 | ACL + Session / Memory 管理 | 检索结果要受知识库权限和会话上下文约束 | 解决多用户隔离、连续对话和记忆接入问题 |
| 答案生成 | 结构化生成 + `[E#]` 引用 | 要求可追溯 | 降低幻觉和不可解释性 |
| 事实校验 | Groundedness / Usefulness Verification | 检索没问题不代表生成就靠谱 | 作为最终质量闸门 |

## 4. 文档解析模块

当前方法

使用统一解析器处理：

- PDF
- DOCX
- PPTX
- Markdown
- HTML
- TXT
- 图片 OCR

为什么这样选

Agentic RAG 的第一步不是模型，而是把原始知识转成可检索结构。
如果文档格式不统一，后续分块、元数据构建和检索都无法稳定复用。

解决什么问题

- 多种文档格式无法共用入库流程
- 文档结构信息在后续处理中丢失

---

## 5. 父子分块模块

当前方法

采用 `Parent-Child Chunking`：

- Parent：用于回答上下文
- Child：用于 first-stage recall

当前流程：

1. 先按结构生成 parent
2. 再从 parent 切 child
3. child 保留 `parent_id`

为什么这样选

RAG 里最常见的矛盾是：

- 小块检索准，但回答时信息不完整
- 大块信息完整，但检索时不够精准

父子分块本质上是把“召回单元”和“回答单元”拆开。

解决什么问题

- 检索时召回精度不够
- 回答时上下文不完整
- 长文档容易“命中一句，缺整段”

## 6. 向量化与存储模块

## 6.1 Dense 表示

当前方法

对子块做 dense embedding，用于语义相似检索。

为什么这样选

Dense 擅长：

- 同义表达
- 语义改写
- 问题和文档文本不完全一致的场景

解决什么问题

- 用户问法和文档写法不同，关键词不完全重合

## 6.2 Sparse 表示

当前方法

对子块正文构建 lexical sparse 表示，用于关键词命中。
当前实现是应用层独立 sparse recall，不是向量库原生 sparse index。

为什么这样选

Sparse 擅长：

- 术语
- 字段名
- API 名
- 型号、版本号、缩写

Dense 对这些精确命中往往不稳定，所以需要 sparse 补强。

解决什么问题

- Dense 容易漏掉术语型问题
- 检索对“精确词”不敏感

## 6.3 Chroma + MySQL 职责拆分

当前方法

- Chroma：只存子块向量和检索元数据
- MySQL：存父子块正文和业务元数据

为什么这样选

向量库最适合做：

- first-stage recall
- metadata filter

关系库更适合做：

- 正文存储
- 结构化字段管理
- 父块回补

解决什么问题

- 向量库塞太多长正文不够优雅
- 父块回补和业务管理不该强依赖向量库

---

## 7. 查询理解模块

## 7.1 Query Rewrite

当前方法

使用 LLM 对原始问题进行检索向改写，输出：

- `query_rewritten`
- `query_intent`
- `retrieval_queries`

为什么这样选

原始问题常常有这些问题：

- 太口语化
- 约束条件不完整
- 缺少核心实体词

解决什么问题

- 提高检索准确率
- 为后续分解和路由提供更好的输入

## 7.2 Query Decomposition

当前方法

将复杂问题拆成多个子问题和多条 retrieval query，并同步初始化 `sub_query_plans`。

为什么这样选

单 query 很难完整覆盖：

- 比较类问题
- 多子任务问题
- 一问多点问题

如果只拆问题、不把子问题变成独立执行计划，后续仍然容易退化成“整体只路由一次、整体只评审一次”。

解决什么问题

- 复杂问题容易只召回一部分信息
- 复合问题里的不同子问题不能走不同工具链路

---

## 8. 路由规划模块

当前方法

新增前置路由节点，根据问题、知识库上下文和联网开关决定走哪条链路：

- `chat`
- `web_search`
- `knowledge_base`
- `hybrid`

当前路由采用“规则门控 + LLM 边界判断”的思路：

1. 先用确定性规则兜住明显场景：
   - 闲聊、问候、轻助手请求优先 `chat`
   - 天气、新闻、股价、行情等实时问题优先 `web_search`
   - 明确提到文档、资料、知识库的问题优先 `knowledge_base`
   - 同时需要内部文档和外部最新信息时走 `hybrid`
2. 再让 LLM 补充 route reason 或处理边界问题。
3. 如果规则已经明确判断为 `chat` 或 `web_search`，不会因为当前选中了知识库就强行改成 `knowledge_base`。

但当前真正生效的执行粒度已经下沉到 `sub_query_plans`：

- 每个子问题独立维护 `route_type`
- 每个子问题独立维护 `need_retrieval`
- 每个子问题独立维护 `need_web_search`

整体级 route 仍然保留，用于事件展示和链路摘要。

为什么这样选

一个真正像智能体的 RAG 系统，不应该把所有问题都硬塞进知识库检索。

比如：

- 闲聊不该走 RAG
- 实时天气类问题不该先在知识库里空转
- 企业内部制度问题也不该默认联网
- 复合问题里不同子问题本来就可能适合不同工具
- 当前选中了知识库，不代表所有问题都必须查知识库

解决什么问题

- 闲聊问题误走检索
- 实时问题误走知识库
- 工具选择僵化
- 复合问题只能共享一个粗粒度 route

## 9. 检索模块

## 9.1 Dense 子块召回

当前方法

在 Chroma 中仅对 `is_parent=false` 的子块做 dense recall。

为什么这样选

子块粒度更适合做 first-stage recall。

解决什么问题

- 用更小的语义单元提升召回精度

## 9.2 Independent Sparse Recall

当前方法

从 MySQL 中加载当前知识库全部 child 正文，构建 sparse 语料并独立召回。

为什么这样选

如果 sparse 只在 dense 候选池里评分，就只能“改排序”，不能“补召回”。

独立 sparse recall 才真正有补召回意义。

解决什么问题

- 关键词型结果没被 dense 拉回来时，仍然有机会命中

## 9.3 多 Query 检索

当前方法

同时使用原始 query、rewrite query、decomposition 产出的 retrieval queries。

为什么这样选

复杂问题不该只靠一个 query。

解决什么问题

- 多表达方式下的召回覆盖不足

---

## 10. 检索融合模块

当前方法

使用 `Weighted RRF` 融合：

- Dense 结果
- Sparse 结果
- 多 query 结果

为什么这样选

Dense 和 Sparse 的分数不容易直接统一比较。
RRF 对这种多路检索融合更稳，工程实现也简单。

解决什么问题

- 多路结果排序难统一
- 单一检索器容易偏科

---

## 11. 父块回补模块

当前方法

在子块排序结果基础上：

1. 提取 `parent_id`
2. 去重
3. 去 MySQL 查询父块正文
4. 把父块内容补回候选项

为什么这样选

检索应聚焦小块，生成应依赖更完整的大块上下文。

解决什么问题

- 小块命中后，模型仍然缺完整上下文

---

## 12. 精排模块

当前方法

使用 Reranker 对融合后的候选再次排序。
当前精排输入优先看父块上下文，同时保留子块 snippet。

为什么这样选

召回解决的是“尽量别漏”，精排解决的是“前几条最能回答问题”。
而父块上下文更接近最终回答所需的证据形式。

解决什么问题

- 召回结果相关但不一定最适合回答
- 前几条候选上下文不完整

---

## 13. 证据模块

## 13.1 Evidence Packing

当前方法

把精排结果转换为结构化证据对象：

- `E1`
- `E2`
- `E3`

为什么这样选

后续生成、引用、验证都应该围绕统一的证据对象工作。

解决什么问题

- 生成阶段无法稳定引用
- 验证阶段无法对齐来源

## 13.2 Evidence Grading

当前方法

对当前证据做逐子问题覆盖度和可回答性判断。

最终只有当所有子问题都被覆盖时，系统才会把整体 `evidence_sufficient` 设为 `True`。

为什么这样选

“检索到内容”不等于“足够回答”。
Agent 需要先判断手头证据够不够，再决定下一步动作。

对于复合问题，更重要的是：

- 不能只看整体“差不多能答”
- 必须确保每个子问题都被证据覆盖

解决什么问题

- 证据不足也直接生成答案
- 一个子问题证据充足，另一个子问题却被忽略

---

## 14. 反思模块

当前方法

通过 reflection 节点为仍未覆盖的子问题生成下一轮检索策略，包括：

- 是否继续
- 如何改写当前子问题 query
- 需要补哪些 retrieval queries
- 当前子问题是否应该改走 web_search

当前默认最多反思：

- `3 次`

为什么这样选

很多失败并不是“库里没有”，而是：

- query 不对
- 检索角度不对
- 维度没展开

而复合问题里，不同子问题失败的原因也经常不同，所以不能只做一次整体改写。

解决什么问题

- 首轮召回不佳
- 多轮信息缺失
- 答案生成后发现证据还不够
- 某个子问题一直没覆盖，但另一个子问题已经足够

---

## 15. 联网增强模块

当前方法

当路由或证据判断认为需要联网时，系统只对 `need_web_search=True` 的子问题调用 web search 获取补充证据。
联网结果会统一转为 `E#` 证据对象，再回到证据判断节点。

为什么这样选

联网结果也不应该“搜到就直接答”，仍然要进入证据闭环。
同时，复合问题必须保证每个需要联网的子问题都拥有自己的搜索机会。

解决什么问题

- 实时信息不在知识库中
- 联网结果无法和知识库证据统一处理
- 复合问题只搜到第一个子问题，后续子问题没有单独搜索机会

---

## 16. 生成与引用模块

当前方法

对于知识型回答：

- 先为每个子问题单独生成结构化答案
- 要求答案中带 `[E#]`
- 再从各子答案里抽取证据编号生成 citations
- 最后聚合成统一的最终回答

对于闲聊路由：

- 不要求证据
- 直接生成对话答案

为什么这样选

同一个系统里既有知识问答，也有闲聊问题。
这两类问题的约束应该不同。

复合问题里如果不先分子问题生成，很容易出现：

- 一个子问题回答很完整
- 另一个子问题只能在尾部补一句“证据不足”

解决什么问题

- 知识问答缺乏可追溯性
- 闲聊问题被误判成“无证据不能回答”
- 复合问题缺少逐项作答结构

---

## 17. 验证模块

当前方法

对生成结果继续做：

- `groundedness`
- `usefulness`

验证失败且还有反思次数时，继续回流到 reflection。

为什么这样选

即便检索没问题，生成阶段仍可能过度发挥。

解决什么问题

- 幻觉
- 答非所问
- 证据和结论不一致

## 19. 检索评估与优化方向

### 当前评估结果

已使用 `mteb/T2Retrieval` 对真实检索链路做过一轮检索评估，报告文件为：

```text
data/evaluation/reports/t2retrieval_eval_kb5_20260521_154148.json
```

评估配置：

```text
kb_id: 5
limit_queries: 200
actual_eval_queries: 136
top_k: 10
dense_top_k: 50
bm25_top_k: 50
rerank_candidates: 50
reranker: enabled
seconds: 164.053
```

核心结果：

| 检索阶段 | hit@10 | mrr@10 | ndcg@10 | recall@10 |
|----------|--------|--------|---------|-----------|
| Dense | 0.977941 | 0.954657 | 0.945744 | 0.960378 |
| BM25 / Sparse | 0.911765 | 0.854044 | 0.846571 | 0.884831 |
| RRF | 0.963235 | 0.928758 | 0.919242 | 0.941675 |
| Rerank | 0.977941 | 0.965686 | 0.942347 | 0.951632 |

从这轮结果看，当前 dense 召回能力较强，sparse 能作为关键词补充，rerank 对 `mrr@10` 有小幅提升，但 `recall@10` 和 `ndcg@10` 不如 dense。

### 当前暴露的问题

这轮检索评估也暴露出几个需要继续优化的点：

1. 评估规模仍受导入语料限制
   本轮请求评估 200 条 query，但当前 `kb5` 只导入了 200 个文档，最终只有 136 条 query 有可用 gold document。若要评估 500 条以上，需要先扩大 T2Retrieval 导入语料。

2. RRF / Rerank 没有明显超过 Dense
   当前 dense 的 `hit@10`、`ndcg@10` 和 `recall@10` 高于或持平 fusion / rerank；rerank 只在 `mrr@10` 上略高。说明多路融合和精排参数仍需要调优，不能默认“链路更复杂就一定更好”。

3. 检索结果存在重复 doc_id
   报告里多个 query 的 `top_doc_ids` 出现重复文档。按 top10 统计，rerank 阶段 135/136 个 query 存在重复，平均每条 query 重复 4.559 个 doc id。重复结果会挤占 top_k 名额，降低 evidence 多样性，并影响后续 Evidence Packing 和答案生成。

4. Rerank 对单条 query 有正负两种影响
   本轮中 rerank 相比 dense 有 6 条 query 指标变好、9 条变差、121 条持平。说明 reranker 有价值，但输入构造和去重策略需要继续优化。

### 后续优化方向

优先级从高到低：

1. 增加去重策略
   在检索融合、父块回补和 rerank 后分别按 `chunk_id`、`doc_id`、`parent_id` 做去重，避免同一文档或同一父块重复占据 top_k。

2. 扩大评估规模
   当前已扩展到 136 条有效 query。若要继续扩大到 500 条以上，需要先重新导入更多 T2Retrieval corpus，并固定随机种子，作为检索回归基线。

3. 分场景评估
   除 T2Retrieval 外，还应补充：

   - HotpotQA 多跳问题检索评估
   - 真实业务 query 评估
   - 术语型、数字型、表格型、长文档定位型问题评估

4. 调整 RRF 权重
   当前 dense 表现强于 sparse，可以基于评估集网格搜索 dense / sparse 权重，而不是固定权重。

5. 调整 rerank 输入
   对比以下 rerank 输入策略：

   - 只输入 child snippet
   - 输入 parent 上下文
   - parent + 命中的 child snippet
   - title / section path + child snippet

   目标是提升 rerank 的 `mrr@10` 和 `ndcg@10`，而不只是提升 recall。

6. 增加多样性约束
   对最终 evidence 做 MMR 或 per-parent cap，避免多个高度相似 chunk 同时进入上下文。

7. 建立检索回归报告
   每次修改 embedding、chunking、RRF、rerank 或 sparse 策略后，都重新输出：

   - hit@k
   - recall@k
   - mrr@k
   - ndcg@k
   - 重复率
   - 平均延迟
   - 每阶段候选数量

### 当前判断

当前检索底座是健康的，但还没有到“企业级稳定最优”的程度。
下一阶段应重点提升去重、多样性、融合权重、rerank 输入策略和规模化评估，而不是盲目继续增加 Agentic 节点。

---

## 20. 一句话总结

当前项目的核心方法论可以概括为：

“把检索、路由、反思、生成和验证拆成可控模块，让系统先决定该怎么找证据、证据够不够，再决定是否回答，从而把普通 RAG 升级为更像智能体的 Agentic RAG。”
