## 架构流程

```
用户网页端提问
  ↓
后端接收 user_id / session_id / question / kb_id
  ↓
保存用户问题到 messages 表
  ↓
加载少量会话上下文
  - 最近 2~3 轮对话
  - session summary
  - working memory
  ↓
根据当前问题 + 少量短期上下文生成 retrieval query
  ↓
双路检索召回
  - Dense
  - Sparse
  ↓
RRF 融合 + rerank 精排
  ↓
根据 user_id / session_id 加载记忆
  - session 短期记忆
  - user/project 长期记忆索引
  - 最近几轮对话
  ↓
Context Assembler 组装动态 prompt
  ↓
发给大模型生成回答
  ↓
保存模型回答
  ↓
更新 session 短期记忆
  ↓
必要时更新长期记忆
```

# 1. 阈值设计的核心原则

阈值不要只看模型最大上下文，而要看这五个因素：

```
1. 成本：上下文越长，输入 token 成本越高。
2. 延迟：上下文越长，首 token 延迟和整体响应时间越高。
3. 噪声：旧历史越多，越容易干扰当前问题。
4. 新鲜度：最近几轮通常比很久以前的对话更重要。
5. 可控性：摘要和长期记忆让系统知道“什么是稳定结论”，而不是每次重新理解一大堆历史。
```

所以阈值设计不是：

```
模型能放 1M token → 那就全塞进去
```

而应该是：

```
模型能放很多 token → 但系统仍然只注入对当前问题有用的上下文
```

企业项目里更重要的是**有效上下文**





## 举个具体例子

假设用户前面聊了 30 轮。

早期说过：

```
长期记忆可以用 Markdown 存本地。
```

后来用户纠正：

```
不对，长期记忆也要存数据库。
```

再后来用户现在问：

```
长期记忆怎么分类？
```

这时候：

### 最近 3 轮原文可能保存：

```
用户：我还是有点迷惑，会话摘要和 working memory 有什么区别？
助手：解释了一部分
用户：长期记忆分类也讲通俗一点
```

### 会话摘要保存：

```
长期记忆使用 Markdown 的方案已被否定，当前确认长期记忆也存数据库。
```

大模型摘要字段案例

```json
{
  "session_goal": "设计 Agentic RAG 的会话记忆系统",
  "confirmed_decisions": [
    "聊天历史、短期记忆和长期记忆都存数据库",
    "Agentic RAG 不使用开放式工具调用"
  ],
  "discarded_ideas": [
    "长期记忆使用本地 Markdown 的方案已被否定"
  ],
  "open_questions": [
    "长期记忆分类如何选择和更新"
  ]
}
```



### working memory 保存：

```
当前回答重点是通俗解释会话摘要、working memory、长期记忆分类和更新。
```



```json
{
  "current_task": "设计数据库版会话记忆系统",
  "constraints_to_add": [
    "短期记忆和长期记忆都存数据库",
    "Agentic RAG 不使用开放式工具调用"
  ],
  "open_questions_to_add": [
    "记忆更新是否全部依赖大模型",
    "长期记忆索引如何选择"
  ],
  "open_questions_to_remove": []
}
```





你看，它们三个各管一块：

```
最近原文 = 保留细节
会话摘要 = 保留历史结论
working memory = 保留当前任务
```
