# 会话记忆与上下文工程设计

上级导航：[`docs/README.md`](README.md) · 对应实现：[会话记忆与上下文工程实现说明](<会话记忆与上下文工程实现说明.md>)

> 文档版本：V1.6 设计基线（2026-09-22）
>
> 本文回答三个问题：三层记忆分别保存什么、如何加载和更新；300k 上下文窗口如何做有效上下文工程；当前只做多轮对话时是否需要 ReAct。

## 1. 设计结论

当前项目应采用“工作记忆（request）+ 短期记忆（session）+ 长期记忆（user/project）”三层结构。三层不是三个重复的摘要，而是三个不同生命周期、不同可信度和不同读写策略的状态空间：

```text
工作记忆：本轮请求的可变任务状态，回答结束即释放
短期记忆：当前会话的连续性，跨本会话多轮保留
长期记忆：经过筛选、确认、带来源和有效期的跨会话事实
```

必须坚持以下边界：

1. 完整消息是事实源；摘要、工作记忆和长期记忆都是可重建的派生状态。
2. 检索证据用于证明回答，用户记忆用于理解用户和任务；两者在 Prompt 中分区，不能混为“上下文文本”。
3. 模型只能提出记忆变更计划，服务端负责权限、作用域、版本、时效、幂等和审计。
4. 300k 是模型的最大输入能力，不是每轮都应该填满的目标。当前多轮问答优先使用 8k～32k 的有效上下文，只有明确需要长历史时才扩展到更高预算。
5. 当前不涉及长任务和自主工具链，不需要为 ReAct 增加一层复杂循环；现有 LangGraph 状态图更适合作为主流程。未来接入工具时再把 ReAct 限定在 Tool Gateway 内。

## 2. 开源项目的借鉴与取舍

| 项目 | 值得借鉴的设计 | 本项目的采用方式 |
|---|---|---|
| [LangGraph Memory](https://langchain-ai.github.io/langgraph/concepts/memory/) | thread-scoped checkpoint 与 namespace-scoped long-term store 分离；记忆写入可在对话后异步执行 | `messages/session_memories` 负责会话态，`long_term_memories` 负责用户/项目 namespace；V1 先同步生成计划、事务提交 |
| [Letta/MemGPT](https://github.com/letta-ai/letta) | core memory 常驻上下文，recall memory 检索历史，archival memory 按需召回；上下文分页而不是无限堆积 | 工作记忆和会话摘要是 core-like 区块；长历史通过摘要、最近轮次和按需检索加载，不直接塞满窗口 |
| [Mem0](https://github.com/mem0ai/mem0) | 从对话中提取候选事实，进行 add/update/delete/noop 决策；写入前做去重和冲突处理 | 保留候选记忆、`create/merge/replace/invalidate/none` 动作和服务端硬校验；不让模型直接写库 |
| [Zep/Graphiti](https://github.com/getzep/graphiti) | 事实具有时间有效性，旧事实被新事实 supersede；区分事件发生时间和系统写入时间 | 为长期记忆保留 `valid_from/valid_to/expires_at/last_confirmed_at`，用 supersede/invalidate 表达用户纠正 |
| [LlamaIndex Memory](https://docs.llamaindex.ai/en/stable/module_guides/deploying/agents/memory/) | 将静态块、聊天历史和可检索记忆组合成受控 memory；按 token 预算裁剪 | `ContextAssembler` 使用 typed sections、分区预算和加载策略；暂不引入其完整 Agent 工具抽象 |

这些项目的共同原则是“记忆不是聊天记录的另一个副本”：记忆必须可解释、可撤销、可过期，并且只在当前问题需要时加载。

## 3. 三层记忆模型

### 3.1 工作记忆（Working Memory）

工作记忆是单次请求的临时工作区，生命周期从 `load_memory` 开始，到本轮回答和持久化计划生成结束。它不写入数据库，不跨会话继承。

推荐结构：

```json
{
  "schema_version": "wm.v1",
  "current_task": "当前问题要完成的任务",
  "goal": "本轮可验证的回答目标",
  "constraints": ["用户明确的格式、范围、语言或安全约束"],
  "open_questions": ["仍未解决的子问题"],
  "active_entities": ["本轮涉及的项目、模块、对象"],
  "working_plan": ["理解问题", "检索证据", "生成并验证"],
  "current_focus": "当前正在处理的焦点",
  "expires_after": "request"
}
```

生成方式：

1. 用原问题、最近对话和会话摘要做 query rewrite，同时生成本轮 working memory。
2. 检索、反思和生成节点只读写当前 State 中的工作记忆；每次反思可以修正 `current_focus/open_questions`。
3. 回答验证失败时，工作记忆可以继续用于下一轮反思；达到上限后直接丢弃。
4. 记忆更新模型可以读取工作记忆来判断长期记忆动作，但不得把工作记忆原样持久化。

工作记忆的判断标准是“对当前回答有用”，不是“未来可能有用”。例如“本轮需要比较两个模块”属于工作记忆；“用户偏好中文回答”属于长期记忆候选。

### 3.2 短期记忆（Short-term / Session Memory）

短期记忆解决同一会话中的指代、连续目标和已确认结论。它由三部分组成，但在概念上属于同一个 session namespace：

```text
原始最近轮次：保留措辞、指代、局部细节和用户最新纠正
滚动会话摘要：保留跨多轮仍有效的目标、结论、否定项、未决问题
会话元状态：会话标题、知识库、归档/分支、摘要游标和版本
```

摘要结构：

```json
{
  "schema_version": "ss.v1",
  "session_goal": "会话总体目标",
  "confirmed_decisions": ["已经确认且仍有效的结论"],
  "discarded_ideas": ["被用户否定或被新方案替代的内容"],
  "open_questions": ["会话中尚未解决的问题"],
  "last_compacted_message_id": 1234,
  "version": 7,
  "updated_at": "2026-09-22T12:00:00Z"
}
```

加载规则：

- query rewrite 阶段优先加载最近 2～6 个用户轮次和会话摘要；当前问题很短或含“它/上面/继续”时扩大最近轮次。
- 普通回答加载“摘要 + 最近轮次”，不加载整个历史。
- 需要追溯旧讨论时，从 `messages` 按 session、分支和关键词/向量检索补充历史片段；补充片段必须标记为 recall，不得伪装成摘要。
- 会话分支只读取当前分支及其祖先快照；分支产生的结论默认不回写其他分支。

更新规则：用户消息和助手消息先写入 `messages`；达到“新增用户轮次、未摘要 token 或字符数”阈值时，再基于上一版摘要和游标之后的原文生成完整新版摘要。摘要更新采用版本校验，冲突时合并而不是覆盖较新的结论。

### 3.3 长期记忆（Long-term Memory）

长期记忆是跨会话可复用的事实，不是所有聊天内容的归档。V1 只接受五类：

```text
user_preference    用户偏好，如语言、回答风格
user_profile       用户稳定属性或背景
project_context    项目背景、技术边界
project_decision   已确认的项目决策
project_constraint 项目约束和不可违反条件
```

推荐记录结构：

```json
{
  "memory_id": "uuid",
  "scope": {"type": "user|project", "user_id": 1, "kb_id": 10},
  "type": "user_preference",
  "key": "response_language",
  "value": "zh-CN",
  "content": "用户偏好使用中文回答",
  "confidence": 0.95,
  "source": "user_explicit|user_confirmed|inferred|imported",
  "status": "pending_confirmation|active|stale|superseded|inactive|deleted",
  "valid_from": "2026-09-22T12:00:00Z",
  "valid_to": null,
  "expires_at": null,
  "last_confirmed_at": "2026-09-22T12:00:00Z",
  "provenance": {"session_id": "...", "message_id": 1234},
  "updated_at": "2026-09-22T12:00:00Z"
}
```

作用域必须是硬隔离：`user` 记忆可跨知识库，`project` 记忆只对对应 `kb_id` 生效。用户明确表达的偏好/约束可以直接进入 `active`；模型从语气推断出的记忆进入 `pending_confirmation`，在确认前不得影响关键决策。

## 4. 长期记忆的时效、冲突和更新

### 4.1 读取流程

```text
当前问题 + 短期上下文
  -> query rewrite / working memory
  -> 按 user_id + scope + status + 时间有效性预筛
  -> 关键词、向量和类型/作用域加权排序
  -> 取 20 条候选
  -> 模型只从候选 ID 中选择最多 6 条
  -> 服务端再次校验权限、状态、expires_at
  -> 仅将选中的长期记忆放入生成 Prompt
```

长期记忆选择不是“取最近 N 条”。排序应综合：当前问题相关度、项目作用域、置信度、最近确认时间、访问频率和新鲜度。模型不可用时只使用达到相关性阈值的候选，不能把全部用户记忆作为回退。

### 4.2 写入流程

```text
回答验证通过
  -> 提取候选事实（只接受用户表达/确认或明确项目决策）
  -> 与同作用域 active 记忆按 key/语义去重
  -> 输出 create / merge / replace / invalidate / none 计划
  -> 服务端校验候选 ID、scope、kb_id、字段和状态
  -> 同一事务写消息、session summary、long-term memory、audit log
```

助手从知识库读到的普通事实不能自动成为用户记忆；否则知识库更新会污染用户画像。长期记忆更新失败不能阻断本轮回答，但必须记录失败事件并允许重试。

### 4.3 时效策略

时间语义分为两种：`valid_*` 表示事实在现实中的有效时间，`created/updated_*` 表示系统何时记录它。用户说“目前使用 X”可设置 `valid_from`；用户说“下个月改用 Y”应创建未来有效或待确认记录；Y 生效后将 X 标记 `superseded` 并填写 `valid_to`。

建议默认策略：

| 类型 | 默认时效 | 更新方式 |
|---|---|---|
| 用户偏好 | 180 天后进入 stale 候选，不自动删除 | 再次表达或确认则续期 |
| 用户画像 | 无固定 TTL，180 天未访问时降权 | 用户纠正时 replace |
| 项目背景 | 90～180 天，项目活跃时续期 | 项目变更时 supersede |
| 项目决策 | 无自动过期，但必须保留来源 | 新决策 replace，旧决策保留历史 |
| 项目约束 | 无自动过期，直到显式解除 | 显式解除才 invalidate |

TTL 不是删除：到期记录进入 `stale`，默认不注入 Prompt，但仍可审计、恢复或重新确认。用户删除应使用 tombstone/`deleted` 状态，避免同一事实被旧消息再次自动恢复。冲突时“用户明确新说法 > 用户确认 > 项目决策来源 > 模型推断”；无法判断时并存并要求确认，不能静默覆盖。

## 5. 300k 上下文窗口的工程设计

模型支持约 300k token，不代表应用层要在每轮构造 300k。应设置四个预算：

```text
MODEL_WINDOW = 300k              模型硬上限
OUTPUT_RESERVE = 8k～16k         输出、结构化 JSON 和引用
SYSTEM_RESERVE = 2k～4k          系统规则与安全约束
REQUEST_BUDGET = 8k～32k 起步    当前请求的有效输入预算
```

只有“用户明确要求回顾长会话、跨多个文档综合、需要历史原文证据”时，才把 `REQUEST_BUDGET` 提升到 64k、128k 或更高。预算提升必须有原因、上限、耗时和成本记录。

上下文加载分三级：

```text
Always-on：当前问题、系统规则、工作记忆、必要证据
Conditional：会话摘要、最近轮次、选中的长期记忆、用户偏好
On-demand：旧消息检索结果、完整文档父块、历史工具结果
```

装配顺序建议为：当前问题 → 任务/工作记忆 → RAG 证据 → 会话摘要 → 最近对话 → 相关长期记忆 → 可选历史召回。证据优先于记忆；每个区块都有独立 token 上限、来源 ID 和是否截断标记。上下文越大，越要用结构化索引和引用，不要只依赖模型“自己注意到”关键信息。

## 6. 动态 Prompt 契约

动态 Prompt 不应是多个字符串直接拼接，而应先构造 typed context，再由 `ContextAssembler` 按任务策略渲染。每个区块都带名称、来源、可信等级、时间和 ID：

```text
SYSTEM
  角色、任务、输出 JSON schema、安全规则

<CONTEXT_SECTION name="task" trust="system">
  当前任务、当前问题、输出要求
</CONTEXT_SECTION>
<CONTEXT_SECTION name="working_memory" trust="state">
  schema_version、current_task、constraints、open_questions
</CONTEXT_SECTION>
<CONTEXT_SECTION name="evidence" trust="retrieval">
  [E1] source=knowledge_base; title=...; section=...; content=...
</CONTEXT_SECTION>
<CONTEXT_SECTION name="session_summary" trust="memory">
  上一版会话摘要及 version
</CONTEXT_SECTION>
<CONTEXT_SECTION name="recent_messages" trust="conversation">
  [M123] 用户：...
  [M124] 助手：...
</CONTEXT_SECTION>
<CONTEXT_SECTION name="long_term_memory" trust="memory">
  [MEM-1] scope=user; type=user_preference; valid_until=...; content=...
</CONTEXT_SECTION>

USER
  当前问题原文

OUTPUT
  严格 JSON；答案中的事实引用 [E#]；不能把 memory 当作知识库证据
```

不同任务使用不同 Prompt policy：

| 任务 | 必选区块 | 条件区块 |
|---|---|---|
| query rewrite | 当前问题 | 摘要、最近轮次、用户语言偏好 |
| long-term selection | 当前问题、候选记忆 | 工作记忆、摘要、最近轮次 |
| answer generation | 当前问题、证据（知识库路由） | 工作记忆、摘要、最近轮次、长期记忆 |
| answer verification | 当前问题、回答 | 证据、引用 |
| memory update | 当前问题、回答、上一版摘要 | 未摘要消息、工作记忆、候选记忆、验证结果 |

动态拼接算法：先计算安全规则和系统区块，再按优先级为每个 section 分配预算；按行/记录截断，不截断 JSON 结构；记录 `loaded_sections/omitted_sections/missing_required_sections/selected_ids/token_usage`。若必选区块无法放入预算，应拒绝调用生成模型并进入压缩或拒答路径。

## 7. ReAct 是否必要

ReAct 是“思考 → 行动 → 观察”的工具调用循环，不是记忆系统，也不是多轮对话的必选框架。当前项目的主要路径是 query 理解、检索、重排、证据判断、生成和验证，属于有明确边界的状态图，LangGraph 已经足够。

当前建议：

- V1/V1.5：继续使用显式 LangGraph；最多保留有限 reflection，不引入开放式 ReAct。
- 引入 MCP、联网、代码执行等工具后：在独立 Tool Gateway 中使用受限 ReAct，设置工具白名单、最大步数、超时、幂等、权限和审计。
- 长任务、计划执行和后台任务出现后：再增加 task state、checkpoint、恢复和人工确认，不要为了“像 Agent”提前引入循环。

## 8. 分阶段落地路线

1. **记忆契约**：统一三层 schema、scope、status、时间字段和 Prompt section 名称。
2. **加载优化**：短期记忆按指代/问题长度自适应窗口；长期记忆增加语义召回、freshness 和 stale 处理。
3. **更新治理**：用户确认入口、冲突合并、TTL 扫描、删除 tombstone、异步重试和审计查询。
4. **上下文扩容**：先将请求预算从 7k 提升为可配置的 8k～32k；完成压缩和长历史召回后，再开放 64k+ 档位。
5. **评测与观测**：追踪记忆命中率、错误注入率、过期记忆使用率、摘要保真度、Prompt token、首 token 延迟和回答引用覆盖率。

## 9. 验收标准

- 同一用户的新会话可以读取已确认的 user 记忆；不同用户和不同 project 不能互相读取。
- 当前请求的工作记忆不会出现在下一会话，且不会被误写入长期记忆。
- 用户纠正旧偏好后，新事实优先，旧事实可追溯但不再注入默认 Prompt。
- 到期记忆默认不参与召回；重新确认可以恢复并写入确认时间。
- 300k 窗口下仍能控制单次预算，并能解释每个 section 为什么被加载、裁剪或省略。
- 生成模型永远能区分 `E#` 证据和 `MEM#` 记忆；记忆不能作为引用来源。
