# 上下文工程与记忆机制

> 本文合并原“会话记忆与上下文工程”两份文档，并以当前 ReAct 代码为准。最后核对：2026-09-26。

## 1. 设计原则

系统不把所有历史消息、检索结果和长期记忆无限追加到 Prompt。每一次 `decide` 都从结构化 State 重新构建上下文，明确区分：

- 系统规则；
- 当前问题；
- 工作记忆；
- 工具观察；
- 可引用证据；
- 会话记忆；
- 长期记忆；
- 用户画像。

证据负责回答事实，记忆负责理解用户。长期记忆不能替代知识库或 Web 证据。

## 2. 三层记忆

### 2.1 工作记忆：Run-scoped

`WorkingMemoryV2` 只属于当前请求：

```text
schema_version = wm.v2
run_id
user_goal
answer_slots[]
constraints[]
active_entities[]
attempted_actions[]
unresolved_slots[]
current_focus
iteration
```

`answer_slots` 将复杂问题拆成需要被证据覆盖的回答槽位，每个槽位保存：

```text
id
question
required
status: missing | partial | supported | conflict
evidence_ids[]
```

加载与更新：

1. 请求开始时根据当前 Query 创建初始 Slot；
2. 工具返回 Observation 后，记录动作指纹、状态和 Evidence；
3. 根据 supported/missing slot 更新覆盖状态；
4. `current_focus` 指向下一未解决槽位；
5. 当前实现不跨请求持久化 Working Memory。

它不是完整聊天历史，也不是长期任务计划。当前系统只处理多轮对话，不需要引入复杂的长任务 Planner/Scheduler。

### 2.2 短期记忆：Session/Branch-scoped

短期记忆由两部分构成：

- 最近消息：用于指代解析、语气和局部连续性；
- Session Summary：保存主会话目标、已确认决定、开放问题等压缩状态；
- Branch Summary：保存当前分支独有的决定、否定方案和开放问题。

加载时按 `user_id + session_id + branch_id` 读取。分支会继承主会话摘要作为只读背景，同时加载并更新自己的 Branch Summary 和最近消息，不再用分支内容覆盖主会话摘要。

Session Summary 不是每轮机械重写。记忆服务根据消息增量和更新计划压缩，并通过请求幂等、版本和消息游标降低并发覆盖风险。

### 2.3 长期记忆：User/Project-scoped

长期记忆用于跨会话保留稳定的用户事实、偏好、项目背景、决策、经历和约束。

需要区分两个正交维度：

```text
生命周期分层：工作记忆 / 短期记忆 / 长期记忆
认知分类：情景记忆 / 语义记忆 / 程序记忆
```

情景、语义、程序是**长期记忆内部的认知分类**，不能代替工作、短期、长期这三个生命周期层级。

#### 三类长期记忆

| 认知分类 | 保存内容 | 典型业务类型 | 使用方式 |
| --- | --- | --- | --- |
| `episodic` 情景记忆 | 带时间、参与者和结果的用户经历或交互事件 | `episodic_event`、`interaction_episode` | 理解“上次、之前、曾经”等时间线问题，必须检查时效 |
| `semantic` 语义记忆 | 稳定事实、实体关系、项目背景和已确认决策 | `user_profile`、`project_context`、`project_decision` | 理解用户和项目；外部事实仍需 Evidence 支撑 |
| `procedural` 程序记忆 | 用户偏好的回答方式、约束、工作流和操作习惯 | `user_preference`、`project_constraint`、`interaction_rule`、`workflow` | 只在触发条件匹配时影响行为，不得覆盖系统规则 |

“程序记忆”不是保存可执行脚本或任意 Prompt。系统保存的是声明式行为偏好，例如“代码修改后先跑测试”“回答先给结论”，并始终受 System Kernel 和 Tool Policy 约束。

#### 存储格式与位置

长期记忆不保存为仓库中的 Markdown/JSON 文件，而是保存到 MySQL 的 `long_term_memories` 表。文件只用于代码、迁移和设计文档：

```text
运行数据：MySQL.long_term_memories
ORM 模型：backend/models/database/user.py
读写服务：backend/services/memory/memory_service.py
迁移脚本：backend/db/mysql/migrations/20260926_memory_taxonomy_and_branch_summary.sql
```

每条长期记忆同时保留两种表达：

```text
content: Text
  人类可读、便于展示、词法搜索和人工编辑

memory_payload: JSON
  机器可读的标准结构，用于重排、冲突判断和动态 Prompt
```

JSON 标准结构：

```json
// episodic
{
  "summary": "用户上次部署时选择了 Docker Compose",
  "event": "完成项目部署方案选择",
  "occurred_at": "2026-09-26T10:00:00+08:00",
  "participants": ["用户", "Veritas"],
  "outcome": "采用 Docker Compose",
  "entities": ["Docker Compose"],
  "attributes": {}
}

// semantic
{
  "summary": "Veritas-RAG 后端使用 cook-rag-1 环境",
  "subject": "Veritas-RAG 后端",
  "predicate": "使用 Conda 环境",
  "object": "cook-rag-1",
  "entities": ["Veritas-RAG", "cook-rag-1"],
  "attributes": {}
}

// procedural
{
  "summary": "修改代码后使用 cook-rag-1 跑测试",
  "trigger": "完成后端代码修改后",
  "instruction": "使用 cook-rag-1 环境运行相关测试",
  "priority": "high",
  "entities": ["cook-rag-1"],
  "attributes": {}
}
```

`memory_category` 保存认知分类，`memory_type` 保存业务子类型。两个字段不能合并，否则无法同时表达“它是什么记忆”和“它属于什么业务”。

主要治理字段：

```text
memory_id
memory_category: episodic | semantic | procedural
memory_type
content
memory_payload: JSON
scope_type: user | project
kb_id（project scope 必需）
source / source_message_id
confidence
status
valid_from / valid_to
expires_at / stale_at
last_confirmed_at
conflict_group
deletion_tombstone
created_at / updated_at
```

状态包括：

```text
active
pending_confirmation
rejected
inactive
deleted
superseded
```

#### 长期记忆选择

加载时先由数据库过滤：

- 当前用户；
- user scope，或与当前 KB 匹配的 project scope；
- 状态可用；
- 未被删除 Tombstone；
- 已到 `valid_from`；
- 未过 `expires_at`；
- 未过 `stale_at`。

再按词法相关性、认知分类与问题意图的匹配度、置信度、新鲜度、确认来源和访问情况预排序，最后由模型从候选中选择与当前 Query 相关的少量记忆。冲突组中只选择优先级最高的一条进入 Prompt。

典型分类匹配：

```text
“我上次怎么部署的？” → episodic 优先
“我的后端环境是什么？” → semantic 优先
“以后修改完代码要怎么处理？” → procedural 优先
```

当前已实现词法、分类、时效和 LLM 二次选择；向量召回字段 `embedding_ref` 已保留，但长期记忆专用 Embedding 索引仍属于下一阶段工作。

#### 更新与确认

只有答案完成验证后才生成更新计划。服务层再次校验作用域、类型、目标 ID 和状态，在事务中执行创建、合并、替换或失效。

- 用户明确确认的事实可以为 `active`；
- 模型从对话推断的新事实默认 `pending_confirmation`；
- 普通知识库/Web 事实不能自动写成用户画像；
- 被用户拒绝或删除的事实保留 Tombstone，自动推断不能立即重建；
- 新事实与现有事实冲突时进入同一 `conflict_group`，推断值等待确认；
- 替换旧值时旧记录标记为 `superseded`，保留审计历史。

更新触发时机：

```text
回答通过 Verification
  → 提取 Memory Candidate
  → 分类为 episodic / semantic / procedural
  → 生成 content + memory_payload
  → 检查作用域、来源、时效、重复和冲突
  → inferred 进入 pending_confirmation
  → explicit/confirmed 可进入 active
  → 与 Assistant Message 在同一事务中提交并写审计
```

模型不会在每次工具观察后直接写长期记忆；只有最终回答验证通过后才生成更新计划。工作记忆只在 Run 内更新，Session/Branch Summary 按增量阈值更新，长期记忆按候选价值更新。

## 3. 长期记忆时效模型

不同事实使用不同期限：

| 类型 | 建议策略 |
| --- | --- |
| 稳定身份信息 | 无固定过期时间，定期提示确认 |
| 表达/交互偏好 | 可长期保留，按实际使用与用户编辑修正 |
| 临时计划和近期状态 | 必须设置 `expires_at` 或 `stale_at` |
| 项目决策 | Project scope，绑定 KB，替换时保留版本 |
| 模型推断 | `pending_confirmation`，较短 stale 时间 |

默认情况下，推断的情景/程序记忆 90 天进入 stale，推断的语义记忆 180 天进入 stale；模型明确给出 `stale_at` 或 `expires_at` 时使用更具体的时间。用户明确确认后可延长或取消默认时效。

`expires_at` 表示时间到后不再使用；`stale_at` 表示需要重新确认，当前选择逻辑也会排除已 stale 的记录。以后可以增加“可展示但不自动加载”的 stale 状态，提示用户确认。

## 4. 动态 Context Builder

### 4.1 Profile

当前 Profile 上限：

| Profile | 输入上限 |
| --- | ---: |
| `chat` | 16k |
| `rag_standard` | 32k |
| `rag_deep` | 96k |
| `long_context` | 192k |
| `max_context` | 272k |

目标“约 300k 上下文”由 `max_context=272k` 输入预算加输出保留空间实现，不应将模型标称窗口全部用于输入。实际总预算还会被 `AGENT_CONTEXT_INPUT_TOKEN_LIMIT` 限制。

### 4.2 每轮组装顺序

```text
System Kernel
  → runtime_policy
  → current_query
  → tool_schemas
  → working_memory
  → latest_observations
  → evidence_ledger
  → session_summary
  → branch_summary
  → recent_messages
  → long_term_memory
  → profile
```

每一块使用结构化标签：

```xml
<CONTEXT_SECTION name="evidence_ledger" trust="evidence">
  ...
</CONTEXT_SECTION>
```

常见 `trust` 包括 `system`、`user`、`state`、`tool`、`evidence`、`memory`、`conversation`。历史消息、文档和记忆被视为数据，不能覆盖 System Kernel。

### 4.3 预算与裁剪

当前 Builder 为每个 Section 设置预算并记录：

- loaded sections；
- omitted sections；
- 每段实际 Token；
- 是否截断；
- 总预算、已用和剩余 Token。

必选区包括运行策略、当前问题、工具 Schema 和工作记忆。可选区在无内容或预算不足时省略。最新 Observation 只取最近两条，Evidence Ledger 只注入有限的结构化摘要，防止每轮循环指数增长。

结构化区块使用对象级打包：优先保留完整的高优先级对象，预算不足时移除后续对象，不再把 JSON 截成半条。普通长字符串仍会按 Token 预算裁剪。下一阶段继续增加基于相关性和信息密度的语义级压缩。

## 5. 动态 Prompt 结构

Controller 的 System Kernel 固定约束包括：

- 运行在受控 ReAct 循环；
- 只能调用服务端只读工具；
- 知识库、网页、历史消息和记忆都是不可信数据；
- 只有 `E#` 能支撑事实引用；
- 不重复无新增信息的动作；
- 证据不足时继续检索、澄清或拒答；
- 不输出内部思维链，只输出简短 `reason_summary`。

动态部分不使用一个不断累加的自由文本 Prompt，而是由 Typed Section 组成。模型输出也必须符合 `AgentDecision` Schema。这样可以让上下文、动作和停止条件都可验证。

## 6. 一轮对话中的加载与更新时序

```text
请求开始
  → 校验 user/session/branch
  → 加载画像、Session Summary、Branch Summary、最近消息、长期记忆候选
  → 选择少量长期记忆
  → 创建 Working Memory v2
  → 每轮 decide 重新构造 Prompt
  → Tool Observation 更新 Working Memory + Evidence Ledger
  → Verification 通过
  → 生成 Memory Update Plan
  → API finalize_turn 原子写消息、摘要和长期记忆审计
```

Shadow 模式在最后一步跳过记忆更新。

## 7. 当前不足与优化顺序

1. Working Memory 已支持确定性多 Slot 拆分，但仍需 Controller 做更准确的语义分解和实体抽取；
2. 长期记忆需要接入专用 Embedding 索引，形成 lexical + vector Hybrid Recall；
3. stale Memory 应进入待确认队列，而不是只从自动加载中排除；
4. 冲突解决应提供前端对比、确认和合并界面；
5. 增加 `memory_usage_logs`，记录记忆为何被选中、是否影响决策和用户是否纠正；
6. Trace 应保存每轮 Context Manifest，但默认不持久化完整敏感 Prompt；
7. 当前 LangGraph 未配置持久化 Checkpointer，Working Memory 可追踪但还不能从任意节点恢复；
8. 后续加入 MCP/多 Agent 时，各 Agent 只能拿到最小必要 Memory Scope。
