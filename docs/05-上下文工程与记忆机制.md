# 上下文工程与记忆机制

> 本文合并原“会话记忆与上下文工程”文档，并以当前 ReAct 实现为准。最后核对：2026-09-26。

## 1. 先区分两个维度

记忆有两个正交维度，不能混为一谈：

```text
生命周期：工作记忆（Run）→ 短期记忆（Session）→ 长期记忆（跨 Session）
认知分类：长期记忆内部的 episodic 情景、semantic 语义、procedural 程序
```

证据负责回答外部事实，记忆负责理解用户和对话连续性。长期记忆不能替代知识库或联网搜索证据。

## 2. 三层记忆

### 2.1 工作记忆：Run-scoped

`WorkingMemoryV2` 只存在于当前 `request_id` 对应的 ReAct Run：

```text
schema_version=wm.v2, run_id, user_goal
answer_slots[], constraints[], active_entities[], known_facts[]
attempted_actions[], unresolved_slots[], current_focus, iteration
```

每个 `answer_slot` 保存问题、是否必需、`missing/partial/supported/conflict` 状态和 Evidence ID。初始化时从 Query 生成，观察工具结果后更新。它不跨请求持久化；Run 失败恢复时由 LangGraph Checkpointer 从 State 恢复。

### 2.2 短期记忆：Session-scoped

短期记忆由以下内容组成：

- 最近消息：处理指代、语气和局部上下文；
- `session_memories.summary`：会话目标、已确认决定、否定项、开放问题；
- Checkpoint 中的本轮 State：仅用于同一 Run 恢复。

Session Summary 在回答通过验证后按增量更新，并使用版本号、消息游标和 `request_id` 幂等，避免并发覆盖。

### 2.3 分叉会话：独立 Session，不是第四层记忆

普通会话请求不加载 `branch_id`，也不会自动选择所谓 active branch。

从某条消息创建分支时，服务端：

1. 新建一个普通 `SessionTable`；
2. 复制截止分叉点的消息，复制后的消息 `branch_id=null`；
3. 仅复制不超过分叉点的安全 Session Summary；
4. `ConversationBranchTable` 只保存父会话、父消息和 `forked_session_id` 血缘。

之后分支使用自己的 `session_id`、消息、摘要、Checkpoint 和 Trace，与源会话完全隔离。没有 Branch Summary，也没有在线隐式 merge。删除血缘记录不会删除其他独立分支；删除分支时先解除外键再删除其 Session 数据。

### 2.4 长期记忆：User/Project-scoped

长期记忆存储在 MySQL `long_term_memories`，不是仓库里的 JSON 文件：

```text
ORM：backend/models/database/user.py
读写：backend/services/memory/memory_service.py
表：long_term_memories
字段：content + memory_payload(JSON) + category/type/scope/status/time fields
```

`content` 是可读和关键词检索投影，`memory_payload` 是受限的声明式 JSON。三类认知记忆示例：

| 分类 | 保存内容 | JSON 重点 |
| --- | --- | --- |
| `episodic` | 用户经历、交互事件、结果 | `event/occurred_at/participants/outcome/entities` |
| `semantic` | 稳定事实、项目背景、已确认决定 | `subject/predicate/object/entities/attributes` |
| `procedural` | 回答偏好、约束、工作方式 | `trigger/instruction/priority/entities` |

程序记忆是声明式偏好，不是可执行代码，也不能覆盖 System Kernel、权限或 Tool Policy。

## 3. 长期记忆只做关键词召回

V1.5 暂不对长期记忆向量化。`embedding_ref` 仅为未来迁移保留，不参与当前召回。

加载步骤：

1. 按 `user_id` 过滤；
2. user scope 或当前 `kb_id` 的 project scope；
3. 排除 `deleted/rejected/inactive/superseded`、Tombstone、未生效和已过期/ stale 记录；
4. 使用关键词交集、内容精确命中、来源、置信度、新鲜度、访问次数和分类意图评分；
5. 无关键词命中不进入上下文；同一冲突组或同一身份键只保留优先项；
6. 取少量候选（默认 Top-K）拼入 Prompt。

当前默认 `MEMORY_LLM_SELECTION_ENABLED=false`，不再追加一次 LLM 二次选择。待关键词召回评测达到基线后，再单独评估是否引入候选内重选。

## 4. 长期记忆加载和更新时机

```text
hydrate_context
  → 读取当前 Session 的摘要和消息
  → 按 user/project scope 做关键词召回
  → 记录 selected_memory_ids 和访问时间
  → 进入本轮动态 Context

回答通过 Verification
  → 模型提出 Memory Update Plan
  → 服务端校验来源、作用域、候选 ID、时效和冲突
  → 与 Assistant Message 在同一事务提交
```

推断记忆默认 `pending_confirmation`，用户明确表达或确认的事实才可直接 `active`。删除/拒绝会保留 Tombstone，自动推断不能立即重建。

## 5. 时效和冲突处理

长期记忆保留历史版本，不物理覆盖：

```text
valid_from / valid_to：事实版本的有效区间
expires_at：明确的失效时间
stale_at：需要重新确认的时间
last_confirmed_at：最近一次用户确认
```

默认推断的 episodic/procedural 记忆 90 天 stale，semantic 记忆 180 天 stale；稳定身份或用户确认事实可不设固定过期，但仍可由用户编辑或失效。

冲突先由模型给出结构化决策：

```text
merge      兼容事实，合并补充
supersede  明确新事实替代旧事实
coexist    不同时间/条件下都成立，条件必须写入 payload/key
confirm    无法可靠判断，等待用户确认
```

服务端护栏不可被模型绕过：只有同一 `user/scope/memory_category/memory_type/normalized_key` 才允许 merge、replace 或 invalidate；目标 ID 必须来自服务端候选集。显式且时间更新的新事实可 supersede，旧值变成 `superseded` 并写 `valid_to/superseded_by`；inferred 冲突默认保持旧值 active，新值 pending。

这个设计借鉴了 Mem0 的结构化 ADD/UPDATE/DELETE/NONE 更新思路和 Graphiti/Zep 的时序事实版本，而不是让模型凭模糊相似度直接删除记忆。模型负责解释“怎么解决”，服务端负责“能不能这样改”。

## 6. 动态 Context Builder

每次 `decide` 都从结构化 State 重建，不把工具原始文本无限追加：

```text
System Kernel / runtime policy
→ 当前 Query
→ Tool Schema
→ Working Memory
→ 最近 Observation
→ Evidence Ledger
→ Session Summary
→ 最近消息
→ 关键词命中的长期记忆
→ User Profile
```

分叉会话只使用自己的 `session_id` 内容；普通会话没有 branch 区块。

每个区块使用结构化标签，历史、工具输出和记忆都标记为数据：

```xml
<CONTEXT_SECTION name="working_memory" trust="state">
  {"schema_version":"wm.v2", "unresolved_slots":["slot-2"]}
</CONTEXT_SECTION>
<CONTEXT_SECTION name="evidence_ledger" trust="evidence">
  {"E1":{"title":"...","support_snippet":"..."}}
</CONTEXT_SECTION>
```

System Kernel 明确要求：只能使用受控工具；事实必须引用 Evidence Ledger 的 `E#`；MEMORY 只能帮助理解用户；证据不足时继续检索、澄清或拒答；不输出内部思维链，只输出结构化 `AgentDecision` 和简短 `reason_summary`。

## 7. 300k 上下文预算

模型标称窗口不是可全部使用的输入预算。当前 Profile 预留输出空间，`max_context` 输入上限约 272k，再受 `AGENT_CONTEXT_INPUT_TOKEN_LIMIT` 限制。

预算顺序：

1. 必须保留 System Kernel、Query、Tool Schema、Working Memory；
2. 优先保留未解决 Slot 相关的 Evidence 和最新 Observation；
3. 保留 Session Summary 和最近消息；
4. 最后保留长期记忆和 Profile；
5. 每个 JSON 区块按完整对象裁剪，不截成半条 JSON；
6. 记录 loaded/omitted sections、每段 Token、总用量和裁剪原因。

当前不涉及长任务计划，因此不引入任务调度器；ReAct 的 `decide → act → observe → decide` 足以覆盖多轮知识库问答。

## 8. 一轮请求时序

```text
API 校验 user/session/kb
  → hydrate_context
  → decide
  → act（knowledge_search/web_search）
  → observe（Observation + Evidence Ledger + Working Memory）
  → decide 循环，直到可答、澄清或拒答
  → verify
  → propose_memory_update
  → finalize_turn 原子写消息、摘要、长期记忆和审计
```

失败节点由 LangGraph Checkpointer 恢复，详见《03-状态、追踪与失败恢复》。工具和异常摘要详见《04-工具系统与检索》。

## 9. 当前边界与后续优化

- 当前长期记忆是关键词召回，不做向量化；
- stale 记忆当前从自动上下文排除，后续可增加待确认队列；
- 未来可增加 memory usage log 和前端冲突对比；
- 多实例部署前把 SQLite Checkpointer 迁移到 Postgres/MySQL；
- 引入 MCP/写工具前先补副作用、人工确认、补偿和重放策略。
