# 系统架构与运行流程

> 当前实现说明，最后核对于 2026-09-26。

## 1. 总体架构

```text
前端
  │  REST / SSE
  ▼
FastAPI API
  │  鉴权、会话/分支解析、请求幂等、Trace Run
  ▼
Runtime Dispatcher
  ├─ legacy       ──> 旧固定 LangGraph（回退与基线）
  ├─ react_shadow ──> legacy 返回答案 + ReAct 只读对照
  └─ react        ──> 受控 ReAct Graph
                         │
                         ├─ Context Builder
                         ├─ Controller
                         ├─ Tool Gateway
                         │    ├─ knowledge_search
                         │    └─ web_search
                         ├─ Evidence Ledger
                         ├─ Verification
                         └─ Memory Update Plan

持久化：MySQL（业务/记忆/Trace）+ Chroma（Dense 向量）
```

入口关系：

- API：`backend/api/v1/endpoints/rag.py`
- 模式分发：`backend/agent/runtime.py`
- 新图：`backend/agent/graph.py`
- 旧图：`backend/graph/graph.py`

## 2. 三种运行模式

### 2.1 `legacy`

旧固定工作流直接承接请求，是当前安全默认值。旧图包含问题改写、拆分、路由、知识库检索、联网、证据判断、反思、生成和验证等固定节点。

### 2.2 `react_shadow`

用户仍得到 `legacy` 的答案。按采样率异步执行一份只读 ReAct：

- Shadow Run 使用独立 `run_id = request_id:shadow`；
- 不提交长期记忆更新；
- 有独立超时；
- 记录答案是否存在、证据数、引用数、迭代数、工具调用数、验证结果及答案哈希等指标；
- Shadow 失败不应影响主请求。

### 2.3 `react`

新图直接承接请求，受总 deadline、迭代预算和工具预算约束。只有该模式经过离线评测、Shadow、灰度和数据库迁移后，才应成为默认模式。

## 3. 新 ReAct Graph

```text
hydrate_context
      │
      ▼
    decide ── final/refusal/clarification ──> verify
      │                                         │
      │ tool_calls                              │ 验证失败且仍有预算
      ▼                                         └──────────> decide
     act
      │
      ▼
   observe
      │
      └────────────────────────────────────────> decide

verify ── publishable ──> propose_memory_update ──> END
```

节点职责：

| 节点 | 职责 |
| --- | --- |
| `hydrate_context` | 校验会话/分支，加载画像、短期和长期记忆，创建 Working Memory v2，暴露允许使用的工具 |
| `decide` | 每轮重新组装上下文，由 Controller 输出结构化 `AgentDecision` |
| `act` | 经 Tool Gateway 授权、校验、幂等和重试后执行工具 |
| `observe` | 规范化 Observation，更新 Evidence Ledger 和 Working Memory |
| `verify` | 检查答案是否可发布、是否有证据支持、引用是否有效 |
| `propose_memory_update` | 只在非 Shadow 且答案成功后生成记忆更新计划 |

## 4. 决策契约

Controller 不返回任意文本动作，而是返回 `AgentDecision`：

```text
type:
  - tool_calls
  - final_answer
  - refusal
  - clarification

tool_calls[]:
  - tool_call_id
  - tool_name
  - arguments
  - purpose
  - target_slots

answer
cited_evidence_ids[]
reason_summary
unresolved_slots[]
confidence
```

`reason_summary` 是简短、可审计的决策摘要，不保存或展示模型内部思维链。事实性结论只能引用 Evidence Ledger 中的 `E#`，长期记忆 `MEM#` 只能帮助理解用户。

## 5. 停止与防失控机制

运行时同时使用多种边界：

- 最大迭代数；
- 最大工具调用数；
- 知识库与 Web 单独调用预算；
- 连续两轮无新增 Evidence；
- 总运行 deadline；
- Controller 错误；
- Verification 最终失败；
- 模型主动输出拒答、澄清或最终答案。

默认预算由 `RuntimeBudget` 和环境变量共同控制。工具错误会变成 Observation 返回图中，不让模型绕过策略层直接执行服务。

## 6. Evidence Ledger

工具输出不会直接散落在 Prompt 中，而是进入统一账本：

```text
EvidenceLedger
  entries: E1, E2, ...
  slot_coverage:
    slot-1: supported / partial / missing / conflict
  conflicts: []
  next_index
```

它负责：

- 给证据分配稳定的运行内编号；
- 去重和记录来源；
- 关联答案槽位；
- 记录冲突；
- 为最终引用构建可追溯来源；
- 为 Verification 提供允许引用的事实集合。

## 7. 会话与数据隔离

所有请求都必须携带服务端解析后的 `user_id`、`session_id`，可选 `branch_id`、`kb_id`。隔离在多层实施：

1. API 校验会话归属和请求范围；
2. Memory Service 校验分支属于当前会话；
3. Tool Gateway 删除模型参数中的身份字段；
4. Tool Policy 使用服务端上下文重新校验 Session 和 KB ACL；
5. 工具幂等键包含 Run、Tool Call、User、Session；
6. Trace API 按当前用户过滤；
7. 分支读取自身消息，且当前不会覆盖共享 Session Summary。

模型不能通过工具参数伪造 `user_id`、`session_id`、`kb_id` 或 `branch_id`。

## 8. 当前差距

- 默认流量尚未切到 `react`；
- Shadow 真实质量、延迟和成本数据尚未完成；
- 节点级 Checkpoint/Resume 尚未实现；
- Decision 没有独立持久化表；
- 原始大体积 Tool 输出尚未通过 `output_ref` 外置；
- 前端分支切换与删除交互仍需完善；
- 生产认证、限流、密钥和网络边界仍需加固。
