# 状态、追踪与失败恢复

> 本文说明当前 ReAct State、Trace 与 LangGraph 持久化恢复的真实边界。最后核对：2026-09-26。

## 1. 三种不同的数据

系统把运行状态、可观测数据和业务数据分开保存：

| 类型 | 作用 | 当前存储 |
| --- | --- | --- |
| Agent State / Checkpoint | 让同一次 Run 从最近安全点继续 | LangGraph SQLite Checkpointer |
| Trace / Attempt / Span / Event / Tool 审计 | 查看每次启动、节点、事件、耗时和错误 | MySQL |
| 消息、会话摘要、长期记忆 | 支撑后续多轮对话 | MySQL |

Checkpoint 不是 Trace，Trace 也不能替代 Checkpoint。前者用于恢复执行，后者用于查询、分析和审计。

## 2. AgentState

`backend/agent/state.py` 的 `AgentState` 是一次 ReAct Run 的完整状态。

```text
身份：run_id, request_id, user_id, session_id, kb_id, runtime_mode
上下文：memory_context, working_memory, context_token_usage, last_context_manifest
决策：decision, pending_tool_calls, tool_calls, observations
证据：evidence_ledger, selected_evidence
控制：iteration, budgets, stop_reason, no_progress_count
输出：final_answer, citations, verification, memory_update_plan
观测：trace_attempt_no, input_tokens, output_tokens, events, latency_breakdown_ms, error
```

工具不能修改 `user_id/session_id/kb_id` 等身份字段。`reason_summary` 只保存简短决策依据，不保存模型内部思维链。

## 3. 当前 Trace

### 3.1 Run、Attempt、Span、Event 与 Context Manifest

`rag_runs` 保存一个 `request_id` 的聚合最终状态。`rag_run_attempts` 保存每次初始执行或恢复；`rag_spans` 按 attempt 实时保存节点开始、完成或失败；`rag_events` 保存结构化事件时间线；`context_manifests` 只保存上下文区块和 Token 用量，不保存完整 Prompt。

恢复重试仍使用同一个 `request_id`：

- 中断时 Run 标记为 `interrupted`；
- 重试时恢复为 `running`；
- 完成后更新为 `completed`；
- 每次恢复创建新的 `attempt_no`，旧失败和错误不被覆盖；
- 相同 `request_id + attempt_no + span_name` 唯一，节点 Span 在执行时实时收口。

### 3.2 Tool Call 与 Observation

`agent_tool_calls` 保存工具名称、规范化参数、参数哈希、状态、重试次数、错误码和 Observation。`agent_observations` 保存结构化摘要、Evidence ID、Slot 覆盖和冲突。

工具调用的持久化唯一范围包含 Run、Tool Call、User 和 Session。节点重跑时，Tool Gateway 会先复用已有 Observation，避免重复调用只读 Provider。

### 3.3 Trace 的边界

当前 Trace 已能定位 attempt、失败节点、事件顺序和上下文装载情况，但仍不是逐 Token、逐状态字段的完整事件溯源：

- Graph State 的完整快照由 Checkpointer 保存，不复制到 MySQL Trace；
- Decision 以脱敏事件元数据记录，没有保存完整模型原始响应；
- 原始大体积 Tool 输出仍应通过 `output_ref` 外置；
- 默认不持久化完整 Prompt，避免敏感信息扩散。

## 4. 持久化 Checkpointer

实现位置：

```text
backend/agent/checkpoint.py
backend/agent/runtime.py
backend/agent/graph.py
```

应用启动时创建一个 `AsyncSqliteSaver`，并用它编译 ReAct Graph：

```text
AGENT_CHECKPOINT_PATH=data/langgraph/checkpoints.sqlite3
thread_id=user:{user_id}:run:{request_id}
```

`thread_id` 包含 `user_id` 与 `request_id`，用于隔离同一次运行的状态。根 Graph 不设置非空 `checkpoint_ns`，否则 LangGraph 会把它解释成子图命名空间。`thread_id` 不能替代 API、Session 和 Tool Policy 的权限校验。

LangGraph 在 Graph 执行的安全边界持久化 State。应用进程重启后，只要仍使用相同 Checkpoint 数据库、同一 `request_id` 和兼容的 State/Graph，就可以读取此前状态。

## 5. 恢复流程

客户端必须在第一次请求前生成并保存 `request_id`。当前前端已将 UUID 随请求发送；如果发生可恢复中断，服务端在 `run.failed` 中返回：

```json
{
  "request_id": "...",
  "resumable": true,
  "stop_reason": "checkpoint_resumable_failure"
}
```

恢复不需要单独的 Resume API。前端在可恢复失败消息上提供“从失败节点恢复”按钮，重新提交相同 Query、Session 和 `request_id`：

```text
读取 checkpoint snapshot
  ├─ snapshot.next 非空
  │    → graph input 传 None
  │    → 从下一个未完成节点继续
  ├─ 已存在 final_answer/error
  │    → 直接返回已完成 State，不重复执行 Graph
  └─ 没有 checkpoint
       → 使用新建 AgentState 从 hydrate_context 开始
```

API 消息写入、最终回答、Trace 和记忆提交均按 `request_id` 去重。因此“响应已生成但网络断开”的重试也不会重复写入用户消息、助手消息或长期记忆。

## 6. 什么情况下会重跑节点

Checkpoint 保证的是从最近已完成的安全边界恢复，不保证恢复任意一行代码：

- 节点完成并提交 State 后，不重复执行该节点；
- 节点执行中抛出未处理异常，只能从该节点前的 Checkpoint 恢复，因此该节点会重跑；
- Tool Gateway 已持久化成功 Observation 时，重跑 `act` 会复用结果；
- 将来引入有外部副作用的工具时，不能只依赖 Checkpointer，必须声明幂等键、重放策略、人工确认或补偿动作。

Controller 的未处理异常会继续向上抛出，不能被转换成普通终态，否则 LangGraph 无法保留正确的失败恢复边界。可预期的工具异常则被规范化成 Observation 返回模型，由模型决定改写参数、换工具、澄清或停止。

## 7. 部署边界

当前 SQLite Checkpointer 适合：

- 单实例开发环境；
- 单机服务；
- 共享本地磁盘且并发有限的部署。

SQLite 文件不是理想的多实例分布式 Checkpoint 后端。多 Worker 或多机器部署应迁移到官方 Postgres Saver，或实现经过并发、事务和序列化测试的 MySQL Saver。切换后必须保持 `thread_id` 规则和 State Schema 兼容。

Checkpoint 可能包含用户消息、记忆和工具观察，生产环境需要配置磁盘权限、备份、加密、清理周期和用户数据删除联动。

## 8. 验收标准

- 同一 `request_id` 能从未完成节点恢复；
- 已完成 Checkpoint 不重新执行 Graph；
- 已成功 Tool Call 不重复调用 Provider；
- 恢复不会跨 User 或 Session；
- 恢复后 Evidence ID、Citation 和记忆更新保持一致；
- 中断、恢复、完成状态能在 Trace 中查询；
- Checkpoint 文件在进程重启后仍可读取；
- 自动化测试会真实关闭并重新打开 SQLite 连接，确认失败节点恢复且已完成节点不重跑；
- 多实例上线前完成 Postgres/MySQL Checkpointer 迁移。

## 9. 参考方案

- LangGraph Durable Execution：Checkpointer + `thread_id` 保存和恢复执行状态；节点内部应尽量确定且副作用需要幂等。
- LangGraph Persistence：Checkpoint 与 Thread 用于读取历史 State 和恢复执行。
- Graphiti/Zep 的时序事实设计用于长期记忆版本治理，不替代 Run Checkpoint。
- Mem0 的结构化记忆更新操作用于约束模型提出的新增、更新、删除或不变决策。
