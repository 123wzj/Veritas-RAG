# 状态、追踪与失败恢复

> 本文专门区分“已经实现的可观测性”和“尚未实现的节点级恢复”。最后核对：2026-09-26。

## 1. Agent State 设计

`backend/agent/state.py` 中的 `AgentState` 是一次 ReAct Run 的运行内状态，按职责可分为六组。

### 1.1 身份与访问范围

```text
run_id, request_id, user_id, session_id, branch_id, kb_id,
web_enabled, runtime_mode, current_query, top_k
```

这些字段由服务端创建。工具调用中的同名字段会被剥离，不能由模型覆盖。

### 1.2 上下文与记忆

```text
memory_context
working_memory
available_tools
context_token_usage
```

`memory_context` 是本轮加载的用户画像、会话摘要、最近消息和长期记忆；`working_memory` 是当前 Run 的任务状态。

### 1.3 ReAct 执行状态

```text
decision
pending_tool_calls
tool_calls
observations
idempotency_cache
evidence_ledger
selected_evidence
```

状态保存本轮决策、已执行动作、观察结果和证据，而不是把工具原始文本直接拼接到消息历史。

### 1.4 循环控制

```text
iteration
budgets
decision_feedback
stop_reason
no_progress_count
last_ledger_size
action_fingerprints
```

这些字段用于控制预算、检测重复动作和终止无进展循环。

### 1.5 最终输出

```text
final_answer
citations
confidence
verification
memory_update_plan
output_tokens
```

### 1.6 运行观测

```text
events
latency_breakdown_ms
error
```

Graph 节点在内存 State 中追加事件和确定性耗时，API 在运行收口时将其中一部分转换为持久化 Span。

## 2. 当前保存了哪些 Trace

### 2.1 `rag_runs`

一行代表一次 API Run，保存：

- request/user/session/kb；
- 最终状态、总延迟、错误；
- runtime mode、预算 Profile；
- 迭代数、停止原因、工具调用数；
- 输入/输出 Token；
- 选中的 Evidence ID、Memory ID；
- Shadow 对比指标。

### 2.2 `rag_spans`

API 在最终收口阶段，根据 Graph 的 `events` 与 `latency_breakdown_ms` 汇总 Span。它适合查看阶段是否发生和耗时，但当前不是节点开始时就实时写入，也没有完整的输入/输出 State。

### 2.3 `agent_tool_calls`

每次工具调用保存：

- Run、Request、User、Session、Branch、KB；
- Tool 名称、参数、参数哈希；
- started/success/failed/denied 等状态；
- retry 次数、延迟、错误码；
- 规范化后的 Observation JSON。

唯一约束为：

```text
(run_id, tool_call_id, user_id, session_id)
```

它既是审计记录，也是持久化幂等依据。

### 2.4 `agent_observations`

保存 Observation 摘要、Evidence ID、已支持/缺失的 Slot、冲突和规范化 JSON。

### 2.5 当前没有持久化的内容

- 每个 Graph 节点执行后的完整 `AgentState`；
- 独立的 `AgentDecision` 历史表；
- 可按序重放的完整 Run Event 流；
- 大体积原始 Tool 输出对象存储；
- LangGraph checkpoint ID 和恢复游标。

因此，“每一步都有 Trace”只能理解为关键事件、耗时和工具动作可追踪，不能理解为每个节点都保存了可恢复快照。

## 3. 现在能否从失败节点恢复

**不能。** 当前代码没有 LangGraph Checkpointer、节点级 State Snapshot 或 Resume API。

目前具备的是：

- Tool timeout 和瞬态错误按 `max_retries` 重试；
- 相同 Tool Call 可复用已持久化的 Observation；
- 消息、反馈和记忆写入有请求级幂等；
- 整个请求失败后可以从 API 入口安全重跑。

这属于“重试与去重”，不是“从失败节点继续”。请求重跑时 Controller 仍会重新决策，不能保证从原来精确的节点和 State 开始。

## 4. 下一阶段 Checkpoint 设计

建议增加两张正式表。

```text
agent_run_checkpoints
  id
  run_id
  checkpoint_id
  parent_checkpoint_id
  node_name
  state_version
  state_json 或 state_ref
  state_hash
  status
  created_at

agent_run_events
  id
  run_id
  sequence
  checkpoint_id
  event_type
  node_name
  payload_json
  created_at
```

约束建议：

- `(run_id, checkpoint_id)` 唯一；
- `(run_id, sequence)` 唯一；
- State 必须带 schema version；
- 大对象写对象存储，数据库只存 `state_ref` 与哈希；
- 事件只追加，不原地修改。

LangGraph 配置建议：

```text
thread_id    = user_id:session_id:branch_id
checkpoint_ns = runtime_version
checkpoint_id = run_id/node_sequence
```

这里的 `thread_id` 不能替代权限校验，它只是 Checkpointer 的命名空间。

## 5. 推荐恢复流程

```text
POST /runs/{run_id}/resume
  1. 校验当前用户拥有原 Session
  2. 校验 Branch 仍属于 Session
  3. 读取最后一个 completed checkpoint
  4. 校验 state_version 与 runtime_version
  5. 重新校验 KB ACL、web_enabled、Tool Policy
  6. 重新计算 deadline 和剩余预算
  7. 检查 pending Tool 是否幂等、是否已有 Observation
  8. 从安全边界节点继续
  9. 生成新的 resume attempt 与审计事件
```

不能无条件重放外部副作用工具。未来引入写操作、MCP 或多 Agent 后，工具需要声明：

- `idempotent`；
- `side_effect_level`；
- `replay_policy`；
- `compensation_handler`；
- 是否需要人工确认。

当前两个工具都是只读工具，恢复复杂度相对较低。

## 6. Checkpoint 粒度

推荐至少在以下安全边界保存：

1. `hydrate_context` 完成；
2. 每次 `decide` 完成；
3. 每个 Tool Call 持久化 Observation 后；
4. `observe` 更新 Evidence Ledger 后；
5. `verify` 完成；
6. 记忆更新计划提交前后。

不要只在 `act` 整批工具执行完后保存，否则并行或多工具场景仍会重复执行已成功的动作。

## 7. 下一阶段验收标准

- 任一节点进程崩溃后可定位最后安全 Checkpoint；
- 恢复不会跨用户、跨会话或跨分支；
- 已成功的幂等 Tool 不重复调用 Provider；
- 非幂等 Tool 默认不自动重放；
- 恢复后的 Evidence ID、Citation 和 Memory Update 可保持一致性；
- State schema 升级有迁移或明确拒绝策略；
- 前端能展示 Run 时间线、失败节点、恢复次数和恢复结果；
- Trace 数据设置保留期和敏感字段脱敏策略。
