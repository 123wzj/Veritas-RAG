# 工具系统与检索

> 当前实现说明，最后核对：2026-09-26。

## 1. 为什么把 RAG 检索改成工具

旧固定流程由路由节点直接决定检索链路。新框架把知识库检索和联网搜索都定义为受控、只读工具，让 Controller 根据当前未解决的问题选择动作，再将结果作为 Observation 返回循环。

这不是让模型直接调用任意 Python 函数，而是执行以下固定链路：

```text
AgentDecision.ToolCallRequest
  → ToolRegistry 查找白名单工具
  → ToolPolicy 校验身份、权限和预算
  → ToolGateway 校验参数、幂等、超时和重试
  → AgentTool Adapter 调用现有业务服务
  → ToolObservation
  → EvidenceLedger
  → WorkingMemory
  → 下一轮 decide
```

## 2. Tool Contract

### 2.1 `ToolSpec`

每个工具声明：

```text
name
version
description
input_schema
required_permissions
risk_level
timeout_ms
max_retries
idempotent
parallel_safe
max_output_tokens
```

Controller 只能看到当前请求允许使用的 Tool Schema，不能调用未注册工具。

### 2.2 `ToolCallRequest`

```text
tool_call_id
tool_name
arguments
purpose
target_slots
```

`purpose` 与 `target_slots` 用于说明这次动作要解决什么问题，不作为服务端授权依据。

### 2.3 `ToolObservation`

```text
observation_id
tool_call_id
tool_name
status: success | partial | empty | failed | denied
summary
evidence[]
evidence_ids[]
supported_slots[]
missing_slots[]
conflicts[]
next_hint
error_code
retryable
output_ref
metrics
reused
```

失败和拒绝也被建模为 Observation，因此 Controller 能依据错误码澄清、换工具或停止，而不是由异常打断整个图。

## 3. Registry、Policy 与 Gateway

### 3.1 Registry

`ToolRegistry` 是工具白名单：

- 注册时拒绝同名覆盖，除非显式 `replace=True`；
- `require(name)` 拒绝未注册工具；
- `specs(names)` 只向模型暴露本轮可用工具。

### 3.2 Policy

`ToolPolicy` 使用服务端 `ToolExecutionContext` 授权：

- Session 必须属于当前 User；
- 总工具调用数不能超过预算；
- `knowledge_search` 必须有 `kb_id` 和 KB 读权限；
- `web_search` 必须由用户或请求显式启用；
- KB/Web 分别有单项调用预算。

模型参数中的以下字段会被删除：

```text
user_id, session_id, request_id, run_id, kb_id, branch_id
```

因此身份、会话和资源范围只有服务端上下文一个事实来源。

### 3.3 Gateway

Gateway 负责：

- 参数指纹；
- 运行内缓存；
- 数据库持久化幂等；
- Pydantic 输入验证；
- Policy 授权；
- timeout 与有限重试；
- Tool Call 和 Observation 审计；
- 将异常规范化为 Observation。

参数指纹为：

```text
sha256(tool_name + canonical_json(arguments))
```

同一个 `(run_id, tool_call_id, user_id, session_id)` 若参数一致且已有 Observation，会直接复用；若 Tool Call ID 相同但参数不同，则返回 `idempotency_conflict`。

### 3.4 工具选择与调用

内置工具在启动时由 `register_builtin_tools()` 统一注册。目前包括：

```text
knowledge_search
web_search
```

每次请求不会把所有工具都交给模型。`hydrate_context` 根据服务端状态生成 `available_tools`：选择了知识库才暴露 `knowledge_search`，显式开启联网后才暴露 `web_search`。Controller 从 Registry 读取这些工具的名称、描述和输入 Schema，通过模型原生 Tool Calling 让模型选择动作。

模型的选择会先转换为结构化 `ToolCallRequest`，再由 Gateway 执行。模型不能直接调用 Python 函数，也不能绕过 Registry、Policy 或服务端身份校验。最终回答、拒答和澄清同样通过 `submit_final_answer`、`submit_refusal`、`request_clarification` 等控制工具提交，避免无结构输出。

### 3.5 异常处理与返回模型的信息

工具失败后，系统不会把完整 Python 异常栈直接放进 Prompt，而是尽量转换为结构化 `ToolObservation`：

```json
{
  "tool_name": "web_search",
  "status": "failed",
  "summary": "联网搜索服务响应超时。",
  "error_code": "tool_timeout",
  "retryable": true,
  "next_hint": "try_other_tool",
  "missing_slots": ["slot-1"]
}
```

不同异常的当前处理：

| 异常类型 | 结构化结果 | 处理方式 |
| --- | --- | --- |
| 权限、Session、KB 或预算不满足 | `status=denied` + 稳定错误码 | 不盲目重试，停止或澄清 |
| 输入参数校验失败 | `invalid_tool_call` | 不使用相同参数重试 |
| 调用超时 | `tool_timeout` | Gateway 按 ToolSpec 有限重试，失败后建议改写查询 |
| Provider 或 Adapter 异常 | `tool_execution_failed` | 有限重试，失败后可换工具 |
| 幂等冲突或调用仍在执行 | `idempotency_conflict` / `tool_call_in_progress` | 拒绝重复执行或复用已有 Observation |
| 正常执行但没有结果 | `status=empty` | 不是系统故障，建议改写查询或澄清 |

Observation 会写入 Agent State 和审计表，下一轮 `decide` 会看到精简后的 `status`、`summary`、`error_code`、`missing_slots` 和 `next_hint`，从而决定改写查询、换工具、向用户澄清或拒答。

推荐的成熟方案是“双通道错误信息”：完整异常类型、消息和堆栈只进入服务端日志、Trace 或告警系统；模型只接收稳定错误码、脱敏摘要、是否可重试和建议动作。当前权限错误与超时已经使用预定义摘要，但未知工具异常仍使用 `str(exc)` 生成摘要，可能暴露内部路径或 Provider 信息，后续应升级为统一 `ToolError` 类型、安全错误映射和 `incident_id`，未知异常只向模型返回通用的 `tool_internal_error`。

## 4. `knowledge_search`

知识库工具是现有混合检索栈的适配器，不重新实现一套检索。

输入支持：

```text
query
search_intent
document_ids
section_paths
top_k
need_parent_context
query_variants
target_slots
```

执行链路：

```text
主查询 + 最多若干查询变体
  → BGE-M3 Dense 召回
  → 独立 BM25 关键词召回
  → Weighted RRF 融合
  → 可选文档/章节过滤
  → BGE Reranker
  → 文档和 Parent 多样性控制
  → Child 支持片段 + Parent 上下文
  → EvidenceItem[]
```

重要边界：

- 当前 Sparse 是独立 BM25，不是 BGE-M3 learned sparse；
- Child Chunk 用于精确命中，Parent Chunk 用于生成上下文；
- `support_snippet` 保留直接支持片段，`snippet` 可包含父块上下文；
- KB ID 来自服务端上下文，不接受模型指定；
- 检索结果最终进入 Evidence Ledger，不能绕过引用和验证。

## 5. `web_search`

联网工具复用现有 Web Provider，输入支持：

```text
query
recency_days
domains
max_results
target_slots
```

当前处理包括：

- Provider 搜索与摘要；
- URL 去重；
- 可选域名过滤；
- 生成 Web Evidence；
- 记录抓取时间和查询。

当前 `recency_days` 会进入元数据，但 Provider 级时间过滤能力仍取决于底层实现，不应在文档中承诺所有 Provider 都严格执行。联网结果同样必须进入 Evidence Ledger 后才能引用。

## 6. 入库链路

当前 V1 上传接口仅接受 Markdown：

```text
Markdown 文件
  → 标题/段落结构解析
  → Parent Chunk
  → Child Chunk
  → Child Dense 向量
  → Child BM25 语料/索引数据
  → MySQL + Chroma
```

MySQL 保存文档、Parent/Child 原文、层级关系和元数据；Chroma 保存 Child Dense 向量及定位元数据。检索命中 Child 后，再从结构化存储回补 Parent。

PDF、DOCX、PPTX、HTML、TXT 和图片解析不属于当前上传能力，规划见《产品需求/多模态解析与检索增强》。

## 7. 证据与引用

每个 Tool Adapter 产生 `EvidenceItem`，常用字段包括：

- `source_type`；
- `title`、`url`；
- `doc_id`、`chunk_id`、`parent_id`、`section_path`；
- `support_snippet`、`snippet`；
- retrieval/rerank score；
- query、tool_call_id、target_slots；
- fetched/published time；
- metadata。

Evidence Ledger 分配 `E1`、`E2` 等 ID。最终答案只能声明实际存在于账本中的 `cited_evidence_ids`，Verification 会检查引用有效性和事实支撑。

## 8. 下一步工具平台优化

在引入 MCP、Skill 和多 Agent 前，先完善统一工具治理：

1. 增加 Tool Schema 版本兼容与弃用策略；
2. 对原始大输出使用对象存储和 `output_ref`；
3. 增加 Provider 级熔断、退避和指标；
4. 将 `risk_level` 接入人工确认与执行策略；
5. 增加副作用、重放和补偿协议；
6. 增加 Secret Scope，不把凭据暴露给 Controller；
7. 支持并行安全工具并发，但保持 Observation 顺序可追踪；
8. 为 MCP Tool 做同一 Gateway 适配，禁止绕过 Policy；
9. 为工具建立成功率、空结果率、P50/P95、重试率和单位成本看板。
