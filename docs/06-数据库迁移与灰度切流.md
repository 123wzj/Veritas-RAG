# 数据库迁移与灰度切流

> 本文描述从 `legacy` 安全迁移到受控 ReAct 的实施与验收顺序。最后核对：2026-09-26。

## 1. 当前状态

- 新 ReAct Runtime、工具层、Evidence Ledger、Context Builder 和记忆治理代码已存在；
- 默认模式仍为 `legacy`；
- 自动化测试与前端构建已在开发环境通过；
- 目标 MySQL 尚需正式执行迁移；
- 真实 Shadow 数据、生产认证和流量灰度尚未完成；
- `backend/graph/` 必须继续保留作为回退与对照基线。

## 2. 数据库迁移

正式脚本：

```text
backend/db/mysql/migrations/20260906_v15_acceptance.sql
backend/db/mysql/migrations/20260926_react_runtime.sql
```

`20260926_react_runtime.sql` 主要增加：

- `rag_runs` 的 runtime、迭代、停止原因、工具数、预算和 Shadow 指标；
- 长期记忆冲突、stale 和 Tombstone 字段；
- `agent_tool_calls`；
- `agent_observations`。

不能只依赖 SQLAlchemy `create_all` 或开发期 `_sync_legacy_schema` 代替生产迁移。迁移前应备份并在副本环境验证执行时间、锁影响和回滚脚本。

建议顺序：

1. 备份目标库；
2. 检查 V1.5 字段是否已存在；
3. 执行迁移；
4. 校验索引、唯一约束和默认值；
5. 用 `legacy` 跑冒烟测试；
6. 再启用 `react_shadow`。

## 3. 配置

关键环境变量：

```text
AGENT_RUNTIME_MODE=legacy|react_shadow|react
AGENT_REACT_MAX_ITERATIONS
AGENT_MAX_TOOL_CALLS
AGENT_MAX_KB_CALLS
AGENT_MAX_WEB_CALLS
AGENT_RUN_DEADLINE_MS
AGENT_CONTEXT_PROFILE
AGENT_CONTEXT_INPUT_TOKEN_LIMIT
AGENT_OUTPUT_TOKEN_RESERVE
AGENT_SHADOW_SAMPLE_RATE
AGENT_SHADOW_TIMEOUT_MS
```

所有 LLM 角色统一使用 `deepseek-v4-flash`。不要在 `.env` 中再用 `DEEPSEEK_PRO_MODEL` 指向其他型号来制造隐式角色差异。

## 4. 分阶段切流

### 阶段 0：离线验证

- 单元测试全部通过；
- 前端生产构建通过；
- 数据库迁移在副本完成；
- 固定评测集覆盖知识库问答、无答案、冲突、Web、记忆和多轮对话；
- 权限、会话隔离和提示注入测试通过。

### 阶段 1：Shadow 1%～5%

`AGENT_RUNTIME_MODE=react_shadow`，低采样运行。关注：

- Shadow 成功率和超时率；
- 答案存在率；
- Evidence/Citation 数；
- Verification 通过率；
- 工具空结果与失败率；
- 平均/P95 延迟；
- 输入输出 Token 和调用成本；
- 与 Legacy 的人工质量对比。

答案哈希完全相同只能作为调试指标，不能作为语义质量标准。

### 阶段 2：扩大 Shadow

逐步提高到 10%、25%、50%、100%。每次只改变一个变量，并观察至少一个完整业务周期。出现权限泄漏、引用错误、循环失控或成本异常时立即回到上一档。

### 阶段 3：ReAct 灰度承接流量

需要增加稳定的服务端分流方式，建议按 User/Session 哈希固定分桶，避免同一会话在两个 Runtime 间来回切换。

```text
1% → 5% → 10% → 25% → 50% → 100%
```

每一档必须支持一键切回 `legacy`。

### 阶段 4：默认 ReAct

将默认模式改为 `react` 之前，至少满足：

- 核心质量指标不低于 Legacy；
- Citation 正确率、拒答合理性和权限测试达标；
- P95 延迟和单位请求成本在目标内；
- Trace 能覆盖生产排障；
- 数据库与 Provider 容量通过压测；
- 前端不依赖 Legacy 特有事件；
- 运维已验证回滚流程。

### 阶段 5：清理 Legacy

100% ReAct 稳定运行一个完整周期后，单独发起清理变更。删除前先冻结 Legacy 评测基线与关键测试，不要在切流提交中同时删除回退代码。

## 5. 验收指标

| 类别 | 指标示例 |
| --- | --- |
| 检索 | Hit@K、Recall@K、MRR、NDCG、噪声率 |
| 生成 | Faithfulness、Answer Relevance、完整性 |
| 引用 | Citation Precision、Citation Coverage、无效 ID 率 |
| 拒答 | 无答案拒答率、可答问题误拒率 |
| Agent | 平均迭代数、工具成功/空结果/重试率、无进展停止率 |
| 记忆 | 选择准确率、错误写入率、冲突发现率、用户撤销率 |
| 隔离 | 跨用户/Session/Branch/KB 泄漏必须为 0 |
| 性能 | P50/P95 延迟、Token、单位请求成本 |
| 稳定性 | Run 成功率、Provider 错误率、Deadline 超时率 |

## 7. 与 Checkpoint 的关系

节点级恢复不是本次切流的既有能力。它可以作为 ReAct 默认化前的增强项，也可以在稳定切流后实施；但如果未来工具具有写副作用或开始执行长任务，则 Checkpoint、重放策略和人工确认必须先于这些能力上线。详细设计见《03-状态、追踪与失败恢复》。
